# Agent instances: isolation, display safety, Linux

Moved verbatim from the old root `AGENTS.md` ("Debugging Atlas Desktop"). Start and stop commands are in [SKILL.md](SKILL.md).

Each instance has its own `HOME`, `ATLAS_HOSTD_DIR` and bridge socket under `/tmp/atlas-agent-<name>/` and its own WebKit data store (WKWebView ignores `HOME`, so `agent_mode::webview_store` gives each instance `WKWebsiteDataStore(forIdentifier:)` under `~/Library/WebKit/<bundle id>/WebsiteDataStore/<uuid>`, in memory on macOS 13; never the bundle's default store, which an instance once rewrote in the user's installed app; `--stop` deletes it, `atlas desktop --agent --gc` deletes those of instances that are gone), so any number of agents run side by side and none touches the user's app, hostd or `~/.atlas`. It runs with `ATLAS_AGENT=1` (debug builds only; a release app ignores it): no Dock icon or tray (`Prohibited` activation policy), never frontmost, and its window sits on a private 2x virtual display (`CGVirtualDisplay`, placed right of his monitors, destroyed with the process; `agent_mode.rs`, `display_mac.rs`, `agent_display.rs`). That display is never occluded, so the page runs at the full 60 rAF/s and ScreenCaptureKit can record it. It is retina (DPR 2); `ATLAS_AGENT_SCALE=1` gives a 1x display. The window is shown only through `agent_display::order_front`, which needs the `ShowGranted` proof of `agent_mode::show_decision`: it fails CLOSED unless the frame re-read from AppKit after placement (and `constrainFrameRect:toScreen:` of it) is wholly inside the display this process created and still owns (vendor `0x4147`, the mode asked for, no overlap with any other display), inset by `SAFE_MARGIN` (the window server outsets windows by a point and AppKit moves them out of the menu-bar band). Any doubt hides the window and exits the instance with code 3 and the reason; a 250 ms watchdog (`guard_user_displays`) is the second line. Starts are serialized: `atlas desktop --agent` (and so `desktop:agent`) takes an exclusive `flock` on `<tmp>/atlas-agent.lock` until the window is shown; a second start waits `ATLAS_AGENT_START_WAIT` seconds (default 120) and then fails naming the lock. **Never start two instances at once, and never start one to test display code before `ATLAS_AGENT_DRYRUN=1 atlas desktop --agent` (create the display, place, decide, log, never order in, exit 0) has logged a sane decision.**

On Linux an instance has its own headless sway and D-Bus session bus (`/tmp/atlas-agent-<name>/run` is its `XDG_RUNTIME_DIR`; no `DISPLAY`, no accessibility bridge, no service activation on its bus), the app refuses to start (exit 3) if its environment points anywhere else, and `debug shot` (page, `--selector`, `--rect`, `--full`, `--window`) is `grim` on that compositor, `debug record` is those frames through `ffmpeg` (the result reports the frames really grabbed), and the mirror and Lab work; the flicker sweep, selection bench, `debug hide` and gesture record/replay do not. Prove isolation there with `hyprctl clients -j` (or your compositor's list) before and after, `pgrep` for the instance's pids after `--stop`, and `ss -xlp` showing no listener of yours under `/run/user/<uid>`.

Prove you did not touch his screen when it matters: list the windows of your pid with `CGWindowListCopyWindowInfo` and check none is on-screen inside a non-virtual display. Check CSP and IPC on the **bundled** build (`tauri://localhost`), not only on Vite.

An instance also never raises native UI outside its window (message boxes such as the watchdog's "page did not start", file panels, notifications, menus popped at the cursor, the browser, the file manager, an editor): macOS places those on the user's active display, not on the virtual one. `native_ui.rs` suppresses them, takes the safe default (an alert is not answered and the app keeps running so you can inspect it; a picker returns nothing; a launcher fails with "not started") and records what it held back: `atlas desktop debug logs --level error` shows `native alert suppressed in an agent instance ...: <title>: <text>`, and the same line is a `native-ui-suppressed` incident in `app.log`. Do not work around it; read the line.
