**Verdict on a UI stream / AG-UI mapping [INFERENCE from the table]:** hostd already emits a broadcast event model with a tool-call lifecycle (`agent_step` for the call with input and output, `agent_tool_output` for the result, `agent_approval(_done)` for the permission interlude), a status machine (`agent_status`) and task snapshots (`crewmate_task`). ## 5. Compatibility constraints and migration risks

- **Wire protocol.** Additive commands, optional args and reply keys do not bump `PROTO` (`protocol.rs:69-76`). Adding a command forces three things: regenerate `testdata/hostd/commands.json` (`UPDATE_FIXTURES=1`, `protocol_golden`), classify it in `client.rs` `QUICK`/`LONG` (`client.rs:120-240`; the test that checks this, per Atlas memory, caught unclassified hostd commands in a mobile batch), and give it a phone scope in `required_scope` or an explicit `Err("not available on mobile")` (`mobile/mod.rs:498-612`). A removed or renamed field means a `PROTO` bump plus the phone's `kAppProto`/`kMinHostProto` (`apps/mobile/lib/core/protocol/protocol_version.dart:6-10`); old apps then show an update state.
- **Old crew servers.** Desktop normalizes older servers in `wire.ts:23-39` (`normalizeCrewmate` repairs a server before #524 that says `working` for a parked task); `audit.ts` still reads `by` for pre-alpha.28 entries. Any new field must be optional with a safe default on the client, and a client must tolerate its absence.
- **On-disk formats.** `Crewmate`, `Task`, `Trigger` are serde JSON with `#[serde(default)]` additions and aliases for renames (`Crewmate` trigger alias `bot`/`from_bot`, `store/mod.rs:107-111`); the `crewmate_list_invalid_cron` fixtures show tolerance for old data. Crews already carry `~/.atlas` data across installs (`atlas crew export` archive has a `manifest.json`, `scripts/crew-e2e.sh:665`), so a new file or field needs an export/import path and a place in `crew-e2e` uninstall cleanup checks (`:694`).
- **Audit schema.** `audit.jsonl` entries are free-form per `kind`; the desktop `AuditKind` union (`audit.ts`) lists 9 kinds while the host writes more, so unknown kinds must not break the filter. Rotation is capped at ~5 MiB: new high-volume kinds (traces) need their own file or limit.
- **Contract fixtures couple three codebases.** The Rust `*_fixture_is_real_payload` tests write `apps/mobile/test/fixtures/*.json`; desktop tests read them from `apps/mobile/...` (`crewmateTaskResumed.contract.test.ts:8`) and the Flutter tests read the same files. Changing a payload shape needs all three to move; the desktop suite cannot run from a checkout without `apps/mobile` and `crates`.
- **Event volume.** `crewmate_task` carries the whole task on every step. Adding finer events (token deltas, per-call) on that path would multiply bytes to every client; hostd's per-connection queue is 8 MiB and a slow client is dropped (`protocol.rs:12-16`). A run stream should be its own event, with its own scope, not more fields on `crewmate_task`.
- **Mobile reach.** Phones reach crews only through the Mac relay (`crew/relay/mod.rs`); the relay filters pushes with `line_scope`, so a new event is invisible to phones until mapped. Terminals, GitHub App, Telegram, voice setup and secrets are refused for phones (`mobile/mod.rs:554-576`).
- **Engines differ.** codex and opencode cannot ask for approval (`data/agents.json` `can_ask`, `approval.rs:472`); their crewmates run unattended, and `crewmate_create` forces `bypass` for them (`handlers/crewmates.rs:47-48`). Any design that relies on a human gate per tool call is true for claude and omp only.
- **Push is not live.** `docs/crew.md:520-524`: the relay is not deployed. Design on in-app and Telegram attention, not mobile push.
- **Isolation.** Where crewmates run as their own Linux users, every new file hostd reads from a crewmate's tree must use the `read_nofollow` helpers (`store/mod.rs:917-919`), and every new tool that touches a crewmate's tree is a candidate for the crew-e2e isolation block (`scripts/crew-e2e.sh:313-660`).

## 6. Dependencies between capabilities

1. Engine parity first: omp gets the atlas MCP server (and, for headless engines, step/tool events) before any capability delivered as an MCP tool (self-observability, registry, external MCP, capture for omp crewmates).
2. Run identity before streaming: a stable `task_id`/run id on `agent_*` events, and steps for headless engines, before an AG-UI adapter, per-run traces or an activity feed means anything.
3. `push_scope` additions before any new event is expected on a phone.
4. Org fields (`team`, `reports_to`) before an organization graph, team memory or per-team policy; the existing `Crewmate` trigger covers delegation without them.
5. Per-crewmate capability grants before external MCP client support (the grant is the allowlist the rails and `decide` need).
6. Audit `task_id` correlation and a per-task read (new filter on `crew_audit`) before traces and any eval that scores a run from its record.
7. A dry-run engine kind before simulation and before evals that must not spend money or touch repos.
8. Memory scopes before feedback loops can write durable lessons anywhere other than one crewmate's file.
