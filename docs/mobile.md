# Atlas Mobile

Atlas Mobile (`apps/mobile`, iOS and Android, preview) is a remote control for the Atlas running on your computer. There is no account and no Atlas server: the phone connects straight to `atlas hostd` on your computer over [iroh](https://www.iroh.computer) (QUIC dialed by public key). It goes direct when the network allows and otherwise through n0's public relays. Traffic is end-to-end encrypted either way, and a relay can't read it.

It works while the Atlas window is closed, because hostd keeps running. The computer has to be awake.

## Pairing

1. On your computer: **Settings → Integrations → Mobile → Pair a phone**. A QR code and a 6-digit code appear for two minutes.
2. In Atlas Mobile: **Add a computer**, then scan the code.

The code works once. Five wrong attempts cancel it. After pairing, the phone is recognised by its own key. Each paired phone is listed under **Paired phones** with what it may do:

| Permission                                  | Allows                                                                                                                                              |
| ------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| See projects, logs, agents                  | project and service state, logs and search, agent tabs and replies, terminal list, a project's changed files and their diffs (`git_status`, `git_diff`); read the images of a crewmate's task, its audit and usage |
| Restart services, run actions, send prompts | restart/start/stop a service, start a stack, run an action (its confirm step is shown on the phone), send a prompt to an agent that is idle or done, stage and unstage files, commit (with the AI message), push and open a pull request (`git_stage`, `git_unstage`, `git_commit`, `git_commit_message`, `git_push`, `git_pr_create`); send a task, with images, to a crewmate (uploading an image is the same permission); answer a crewmate's question (`crewmate_answer`) or a card, including a secret it asks for (Face ID first) |
| Answer agent permission prompts             | allow or deny a Claude Code / Codex tool call                                                                                                       |
| Watch terminals                             | live terminal output                                                                                                                                |
| Type in terminals                           | keystrokes; the app also asks for Face ID / biometrics before each session                                                                          |

**Revoke** cuts the phone off immediately and forgets it, and takes its push tokens with it: on this computer, and on every crew server behind it (the Mac sends each one `push_forget` with the phone's node id; a crew server that is unreachable at that moment logs it, and the phone is cut off from the Mac either way). A token the phone registered on a crew server through the Mac is stored there under the phone's own node id (the Mac stamps it from the phone's connection; whatever the phone puts in `node` is overwritten), so revoking the phone on the crew server itself clears it too. A phone can never run shell commands through `exec`, read or write files, change its own permissions or manage devices.

**No computer at hand?** Under the scanner, **Explore a demo** opens a computer that lives in the app (`apps/mobile/lib/core/demo/demo_computer.dart`): sample projects, services, logs, agents with a permission prompt to answer, a crew. It answers the same protocol as hostd, connects to nothing and is not saved; **Settings → Leave demo**, pairing a real computer or relaunching ends it. It is how App Review and Play review use the app (their review notes point to it), and the tests run every screen against it.

### Pairing fails with a VPN or WARP on

The pairing code carries this computer's key, its relay and its direct addresses (`addrs`). hostd publishes only the addresses of real LAN interfaces, private IPv4 first, then ULA and global IPv6. It leaves out loopback, link-local (`fe80::`, `169.254.`), CGNAT `100.64.0.0/10` and any address that only a tunnel owns (a `utun`/`tun`/`wg`/`tailscale` interface, or any interface flagged point-to-point), because a phone on the LAN cannot reach those (`crates/atlas-host/src/mobile/addrs.rs`, #113). If every address is a tunnel's, they are published anyway rather than an empty list; the relay still connects.

What this does **not** settle: whether a phone on the same Wi-Fi reaches the computer's LAN address while a full-tunnel VPN is on. Packets from the phone arrive on `en0`, but the replies leave by the route the VPN installed; a VPN that captures the default route (WARP in its default mode) can send them into the tunnel, so the direct path never completes. That depends on the VPN's routing and split-tunnel rules and needs a phone on the network to check. Until it is measured, expect the relay (`ATLAS_MOBILE_RELAY` unset) to carry the connection, and if pairing does not complete:

1. Make sure `ATLAS_MOBILE_RELAY=0` is **not** set (it turns the relay off, so only the LAN addresses remain).
2. Pause the VPN, or add the LAN (`192.168.0.0/16`, your Wi-Fi subnet) to its split-tunnel exclusions, then pair again.
3. Check what is published: Settings → Integrations → Mobile shows the addresses in the pairing link (`addr=` parameters).

### The app and the computer disagree on the protocol

On every connect the phone asks hostd's `info` once and compares its `proto` with the two constants in `apps/mobile/lib/core/protocol/protocol_version.dart`: `kAppProto` (what this app speaks, mirrors `PROTO` in `crates/atlas-host/src/protocol.rs`) and `kMinHostProto` (the oldest hostd it works with). Bump `PROTO` and `kAppProto` together on any non-additive wire change (a renamed or removed command or field, a changed meaning); a new command or an optional field is additive and needs no bump. Raise `kMinHostProto` only when the app starts to need something an older hostd lacks.

- **hostd older than the app** (`proto` below `kMinHostProto`, or no `proto` at all, which is protocol 1): the home screen says **Update Atlas on <computer>** and to run `atlas update` there; the Crew tab and a crewmate's chat show the same one line. Nothing else is asked of that computer, so there is no `bad request` per command.
- **hostd newer than the app**: only when its `info` carries `min_client_proto` above `kAppProto` (hostd does not send it today): **Update Atlas Mobile**. Without that field a newer hostd is assumed additive.

A mismatch is not an outage, so the phone does not retry it in a loop: it checks again when the app comes to the foreground, on pull to refresh and on **Try again**, and the state clears as soon as the versions agree.

## Review and ship from the phone

A project's page has **Review changes**: the changed files (staged and not), the diff of each (the same code block the chat uses, `diff` mode), a stage toggle per file, **Commit** (type a message or **Write with AI**, which runs the agent CLI of Settings → Git on the staged diff exactly as the desktop does: secrets withheld, lockfiles named), **Push** and **Open a pull request** (`gh pr create`). It is a fixed set of hostd commands, never a git command line: `root` must be a registered project or one of its worktrees (compared after canonicalization), paths must be relative and stay inside it (a symlink out is refused), the commit message goes on stdin, a push is never forced and only sends the current branch (`--set-upstream origin` the first time). Reading needs the first permission; everything that changes a repo or reaches GitHub needs the second. The audit log records the call but only the length of the message, title and body. hostd does the work itself (`crates/atlas-host/src/git.rs`, parsers and the commit-message logic shared with the desktop in `atlas_core::git_review`), so it works with the Atlas window closed; `gh` must be signed in on the computer.

## Approvals

Claude Code and Codex run `atlas hook … permission-request` before showing their own prompt. While a phone is connected, hostd shows the prompt on the phone and waits up to 55 s for Allow or Deny. With no phone connected, it answers nothing at once, and the agent asks in the terminal as usual. Re-run `atlas setup claude-code --apply` / `atlas setup codex --apply` once so the hook is registered with its 60 s timeout. omp approvals are shown as "needs you" but answered on the computer.

## Agents on the phone

An agent's chat is read from its session file (`agent_history`, `crates/atlas-host/src/agents/history.rs`): omp, Claude Code and Codex transcripts become one timeline of turns, thinking, tool steps (intent, status, clipped output) and, for omp, the subagents a `task` call started, each read from `<session>/<Name>.jsonl` (the phone names a subagent, never a path). omp subagents load the status extension in the parent's terminal; hostd recognizes their session files under the parent's session dir and never lets them rename, retarget or finish the pane (an approval still blocks it). The title is omp's session title (the `title` slot, else the session header's, else the first thing the user typed, one line: never an injected block and never a subagent's assignment). **The tree** (`agent_tree`, `crates/atlas-host/src/agents/tree.rs`) lists the agent and every subagent, however deep, as flat nodes `{id, parent, name, agent, model, status, task, duration_ms, tokens, cost, tool_count, now, report, updated_at, agent_type, thinking, requests, active_ms, context_tokens, context_window, recent}` (the root is `id: ""`, and also carries `todos`). omp ids are the dotted names omp uses on disk (`Scout`, `Scout.Deep`: `<session>/Scout/Scout.Deep.jsonl`); Claude Code's are `agent-<id>` from `<session>/subagents/`; Codex has none, so its tree is the root alone. `status` is `pending|running|completed|failed|aborted|idle`: the parent transcript's `async-result` (`<task-result status=…>`) decides how a subagent ended; before it, `running` while its lock file (`.<Name>.jsonl.lock.os`) exists or its transcript changed in the last minute, `completed` once `<Name>.md` exists, else its last `stopReason` (`error` → failed, `aborted` → aborted), else `pending`. `now` is the intent (or `tool: detail`) of the node's open tool call; tokens and cost are summed from the node's own transcript. The rest feeds the hub, all from that same transcript: `agent_type` (omp's agent definition, `task`/`scout`; null on the root), `thinking` (last `thinking_level_change`), `requests` (assistant messages), `active_ms` (time between consecutive entries, gaps over 5 minutes counted as parked), `context_tokens` (the last request's prompt: input + cache read + cache write), `recent` (the last 8 tool calls, `{at, tool, intent, status: running|ok|error}`). `context_window` is only what omp itself reported in the parent's `task` result (`details.progress[].contextWindow`, present for synchronous spawns); hostd never guesses a window from the model name, so an agent without one shows no context bar. The root's `todos` is `{phases: [{name, tasks: [{content, status}]}], done, total}` from omp's latest todo state: the last `user_todo_edit` entry or successful non-`view` `todo` result in the transcript (the same rule `todo-tracker.ts` rehydrates by); other agents have `null`. `agent_history` takes a dotted `sub` (every segment `[A-Za-z0-9_-]`, never a path) and also returns `result` items (a subagent finished) and `compaction` items. What omp injects as a *user* turn is not one: `<irc from="parent" agent="Main">…</irc>` (behind the `[Wait interrupted by message]` marker or not) becomes `{kind: irc, from, agent, text}`, a `<system-notice>`/`<system-injection>`/`<system-reminder>` block `{kind: notice, text}`, and omp's `advisor` message one `{kind: advisor, severity, text}` per note (`blocker`, `concern`, `nit`…). `messages` for older phones keeps typed user turns only. **Steering**: `agent_send` with `steer: true` types into a *working* omp agent, which queues it for the running turn; Claude Code and Codex, and omp without `steer`, still refuse while the agent works. Stop sends Escape (`agent_interrupt`, only while the agent works); slash commands are typed like any message. **New agent** (`agent_launch`) asks Atlas Desktop over `~/.atlas/desktop.sock` for `terminal_create` in the project, so it needs the desktop running. Both need the **act** permission.

**The hub on the phone** (`apps/mobile/lib/features/agents/agent_hub_screen.dart`) is omp's Agent Hub: the app-bar button opens the roster of the pane's agents (a long-press on a crew chip opens that agent's detail directly) with `N running · M parked`, the totals (cost, active time, requests, tools, tokens), a **Flat / By parent** switch (the tree indents; flat names `↳ parent` on each row) and **All / Running / Done / Failed** filters. A row is the status ring, the dotted name, type · model · thinking, the task in one line and its numbers with the last activity. Tapping it opens the **detail**: Task, Current (the running tool), Usage with the context bar (`292K/1M 29%`, only when omp reported a window), Lineage (spawned by, children: each a link that opens that agent's detail), the todos for the main agent, Recent activity (timestamped tool rows with their outcome) and the report. Its buttons stay pinned under the scrolling content: **Open conversation**, **Back to parent** (or Main) and **Message**. In the chat, a persistent breadcrumb (`Main › Scout › Deep`, every crumb a chip, `Main` first) is on screen while a subagent is focused. The main agent shows a **Waiting on N jobs** strip (running subagents, a tiny bar of each one's context use, each a link) and a collapsible **todo card**; IRC, notice and advisor items render as compact cards (advisor by severity: blocker red, concern amber), never as the user's bubbles. hostd can only type into the main agent's terminal, so a message written while a subagent is focused is labelled *Message Main about <name>* and sent to the main agent as `Tell <id>: …` (as a steer while it works); only omp relays it, so Claude Code and Codex show no composer on a subagent. Claude Code and Codex degrade to what they have: a Claude agent's subagents list flat, a Codex agent is the root alone.

### Worktrees and agents in a worktree

The phone lists, creates and removes git worktrees of a project and starts an agent in a chosen one, **with the desktop app closed**: hostd does it itself (an agent launch goes to the desktop's tab when the app is running) (`crates/atlas-host/src/worktrees/`). The desktop uses the same code and the same registry file (`~/.atlas/desktop/projects.json`, edited under a cross-process lock), so both see the same worktrees, in the same folders (`<workspaceDir>/<repo>/<name>`), with the same branch rules, port offsets and `worktree:` hooks of `atlas.yaml` (`shared`, `seed`, `setup`, `archive`).

| Command | Scope | Does |
|---|---|---|
| `worktree_list {project}` | `read` | the repo and its worktrees (`id`, `path`, `branch`, `main`, `dirty`, `portOffset`), git read live |
| `worktree_create {project, name?, base?}` | `act` | `name` is slugged (empty picks a sea name), `base` must be an existing ref (never an option); `setup` runs headless and its result comes back, a failing setup keeps the checkout |
| `worktree_remove {id}` | `act` | only when nothing would be lost, the desktop's auto clean-up rule: answers `{kept: "dirty" \| "secrets" \| "unpushed"}` otherwise. Never forced, the branch stays. A main checkout is refused |
| `agent_launch {project, agent, prompt?, worktree?}` | `act` | with Atlas Desktop running it opens a real tab there (`terminal_create` on the desktop's control socket, with the worktree's folder); with the app closed (nothing listens on the socket) hostd spawns the agent itself in that folder, never with the agent's yolo flags. A desktop that answers with an error is not "closed": the error is returned, nothing is started behind its back. The project's main checkout without `worktree` |

All of them take registry ids, never paths, and ignore SSH checkouts (the desktop owns those). The lab hostd forwards `worktree_create`, `worktree_remove` and `agent_launch` to your real hostd and answers `worktree_list` itself.

## Crew on the phone

Crewmates live on crew servers (`atlas crew install`, see [Atlas Crew](crew.md)). A phone reaches one of two ways. **Directly:** the phone is paired with the crew server itself (its own iroh identity, the same pairing as a Mac), so the crew works with every other computer off. **Through a Mac:** Atlas Desktop reaches the server over SSH and the phone talks to its paired Macs, which relay. The Mac's hostd relays: `crew_servers` lists the crew servers in `~/.atlas/desktop/crew-servers.json`, and `crew_call {server, cmd, args}` runs a command there through hostd's own SSH connection to it (`$HOME` and the token read over `ssh`, then `ssh -N -L` to its `hostd.sock`, like the desktop; `crates/atlas-host/src/crew/relay/`). The crew server's pushes come back as `{"ev":"crew_event","server":…,"event":…}`. A relayed command needs the scope it would need sent to the Mac (`mobile::required_scope`); terminals and secrets are never relayed, and a relayed push passes the phone's scopes like the push inside. The phone shows each crew server as its own computer behind the Mac (`CrewTransport`, `crewDevicesProvider`). The Mac must reach the crew server with this user's SSH key (`BatchMode`, no prompt). macOS and Linux only.

### Pair a crew server with no computer in the loop

```bash
atlas crew pair user@server            # a QR code, a 6-digit code and the link; --port N for an SSH port other than 22
```

From any machine that can SSH to the server (a laptop, a tablet with an SSH app), `atlas crew pair` asks the crew server's own hostd for an invite as the crew user (`atlas hostd --mobile-pair` on the server: the same `mobile_pair_start` the desktop uses, one code, 120 seconds, five wrong tries), waits for the relay address so the link works off the LAN, and prints the QR (black on white, whatever the terminal theme) with the code and the link. In Atlas Mobile: **Add a computer**, scan it. The phone pairs with the crew server directly and keeps it in its list of paired computers, so it is listed with no Mac on. Pair as many phones as you like, one invite each.

**Invites that were missed.** The desktop's **Add crew server** also pushes an invite to your phones (`computer_invite`), and stores it on the computer for the life of its code (`mobile_invites`, `read`). The phone now asks every computer it reaches for its pending invites when it connects, so one made while the phone was off or out of range shows up in the Crew tab as **New crew server**. An invite lives as long as its code (120 seconds) and is dropped when a newer code replaces it (a second pairing started), since its link would answer "bad code".

### Questions from a crewmate (`ask_user`)

An agent that cannot go on without an answer asks (`ask_user`) and waits up to 30 minutes. The question is on the task (`ask`: `id`, `question`, `options` with `key`/`title`/`subtitle`, `allow_text`), so the thread shows a card with the question, one button per option and, when the agent allows free text, a field. Tapping an option sends `crewmate_answer {id, ask_id, key}`, typing sends `{id, ask_id, text}` (`act`); the agent's call returns the answer and the card closes with the task's next push. hostd refuses an answer to an ask that is closed or unknown, and the card keeps the question with that message. The card reads the task exactly as hostd serializes it (fixture `apps/mobile/test/fixtures/crewmate_task_ask.json`, written by `ask_user_fixtures_are_real_payloads_and_the_phones_answer_wakes_the_agent`).

### Images on a task

The composer has an image button (**Attach image**): **Take photo** (camera) or **Photo library**, up to 4 images of at most 5 MiB (png, jpeg, webp, gif by their bytes; anything else is refused with its name before it is uploaded). Photos are scaled to at most 2048 px and re-encoded at 85 % quality first, so a camera shot fits the cap. The pending images show above the field with a remove button; **Send** needs text (a task is a prompt) and keeps text and images with the server's reason on screen when the task is refused. `image_picker` asks for camera access only when you take a photo, and the photo library through the system picker; the iOS usage strings say so.

In the thread, a task's images show right-aligned under its prompt, fetched from the crew server when they first appear and kept for the session (tap one to see it large). They travel through the Mac's `crew_call` like every other crew command, in pieces of at most 512 KiB (a protocol line is at most 1 MiB): `crewmate_attachment_put` (needs `act`) uploads, `crewmate_attachment` (needs `read`) fetches. A phone granted `act` but not `read` can send an image and then sees it as "Tap to retry" with `forbidden: read`; the rest of the thread is unaffected. The push relay never sees an image. The demo computer answers both commands and enforces the same caps, so the screens run against it.

A task that waits on a card the owner decides (Atlas's guards refused it, or a [UI task](crew.md#ui-tasks-and-proof) finished without two captures of its own) shows the captures the agent took as thumbnails (tap to enlarge) with the reasons on its card in the chat, and the Crew tab's **Captain's call** lists it with the same captures and **Retry** / **Override** in place (`crewmate_action_answer`, scope `act`; the list reads it from `crewmate_list.waiting_task`, scope `read`). In the chat card, **Add a screenshot** (camera or library) attaches a marked screenshot to the retry: it goes up like a task's images, is stored on the task as yours and staged for the agent; images with an override are refused. A task you send can be marked `ui` (`crewmate_task {ui}`); the agent's captures also show under its reply once it is done. The demo computer raises a `prove_ui` card for a task sent with `ui` and answers both answers, so the screens run against it.

### Audit, usage, routines and crew settings

What the desktop keeps in a crewmate's settings is on the phone too, over commands hostd already had (`apps/mobile/lib/features/crew/ops/`); the demo computer answers every one of them.

| Where                                   | Screen                                                                                                                                                                                       | Command                                          | Permission |
| --------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------ | ---------- |
| Crewmate profile → **Audit**            | everything the crewmate ran or asked to run, newest first, filtered by Tool calls / Approvals / Tasks / Settings; tap an entry for the whole record and **Copy**                              | `crewmate_audit`                                 | read       |
| Crew tab → options → **Crew audit**     | crewmates created or removed, crew paused or resumed                                                                                                                                         | `crew_audit`                                     | read       |
| Crewmate profile → **Usage**            | tokens today / 7 days / 30 days, a 30-day chart, the cost an engine reported, and what the engine CLIs expose about their limits (today they expose none, and hostd says so)                  | `crewmate_usage`, `engine_limits`                | read       |
| Crewmate profile → **Routines**         | add, edit, switch off or remove a cron routine (a prompt it runs on a schedule); the whole list is saved at once and hostd's cron parser has the last word, its message is shown when it refuses | `crewmate_routine_set` (list: `crewmate_list`)   | act        |
| Crew tab → options → **Crew settings**  | whether long replies are summarized and by which model; a phone with `read` only sees them, it needs `act` to change them                                                                    | `crew_settings_get` / `crew_settings_set`        | read / act |
| Crew settings → **Engine sign-in**; the *Sign in here* button of a "Sign in to …" card | whether claude, codex, omp and opencode are signed in on the crew server (checked each time the screen opens), and **Sign in**: a terminal on the server that runs only that engine's login command, opened in the terminal screen (typing stays behind Face ID) | `crew_engine_status`, `crew_engine_login` | read / act |

All of them also work for a crew server behind the Mac (`crew_call` needs the same scope as the command inside). The audit never contains a secret's value, only its name, and a phone has no secrets editor (`crewmate_secret_set` stays refused). **A secret a crewmate asks for is allowed from the phone**: the `provide_secret` card sends it with `crewmate_action_answer` (`act`), after Face ID (or the device passcode; a device that cannot ask sends nothing and says why). The phone's audit log keeps the command and the secret's length, never the value, at any depth (a relayed `crew_call` carries it inside `args`), and the crew server's audit holds only its name. `crewmate_list` now carries each crewmate's `routines` so the editor starts from what is stored.

**Engine sign-in has one limit by design.** The status works behind the Mac too, but the sign-in is a terminal and terminals are never relayed, so `crew_engine_login` is refused through `crew_call`: pair the phone to the crew server itself to sign an engine in. The terminal starts only the login command hostd allows for that engine (`claude auth login`, `codex login --device-auth`, `omp login`, `opencode auth login`), as the crew user, with no agent pane; `engine_login_started` goes to the crew audit with who asked and for which engine, never what is typed. A task that fails with the engine's own auth error flips it to *Needs sign-in* at once and hostd pushes `crew_engine_auth`.

### Push notifications

**Status (checked 2026-11-14): in the code, not live.** Everything below ships: hostd's notifier (plain agents and crewmates), `push_register` with a relay grant, revoke clearing tokens, the app's registration and its Notifications row in Settings, and the two bring-up scripts. What is **not** done is switching it on: the relay is not deployed (`push.codeatlas.com.br` does not resolve, so `curl -X POST https://push.codeatlas.com.br/v1/register -d '{"token":"x"}'` fails with "could not resolve host"), and the apps are built without Firebase config (no `GOOGLE_SERVICES_JSON`/`GOOGLE_SERVICE_INFO_PLIST`, no APNs key). So today no phone receives a push, and nothing here has been seen working on a real phone. "Bringing push up" below is the exact list of what turns it on. Re-run that `curl` after step 2: when it answers `200`, update this paragraph.

The app gets a push for a crewmate's finished task or approval prompt, and for a plain agent on your Mac (omp, Claude Code, Codex in a terminal) that finished or needs you, only while it is not connected. Registration (`core/push/`): when Firebase is configured the app takes its FCM token, asks the push relay for the token's **grant** (`POST /v1/register`, `ATLAS_PUSH_RELAY` dart-define, default `https://push.codeatlas.com.br`) and sends `push_register {token, platform:"fcm", grant}` to every connected computer that can notify: the paired Macs, whose `info` lists the `push` cap (every hostd from the plain-agent push change on), and the crew servers behind them (the `crew` cap). The demo computer is skipped, and a hostd older than the `push` cap is not asked. It does this again on every launch and reconnect and when FCM refreshes the token, so an old registration without a grant is replaced the first time the updated app opens. Without a grant the app registers nothing and retries on the next connect, and Settings → Notifications says why in one line ("Notifications are on", or the first reason: the relay unreachable, rate limited or down with its HTTP status, a computer too old to send notifications, or one that refused `push_register` with its own error). Tapping a push whose agent has closed says "That agent has finished"; when no computer has the agent and one could not be asked, it says "<computer> is not reachable". The relay refuses a notify without the grant ([services/push-relay](../services/push-relay/README.md)). Builds without `GOOGLE_SERVICES_JSON` / `GOOGLE_SERVICE_INFO_PLIST` have no token and skip all of this.

**Plain agents (the Mac's hostd, not the desktop app: it works with the Atlas window closed).** hostd stores the token with the paired phone's node id (taken from the connection that sent `push_register`, which needs only `read`, as before) and watches every agent pane's `agent_status`. It notifies on a transition, never on a heartbeat:

| kind | when |
|---|---|
| `agent_done` | a pane that worked goes to done, or its program exits (idle) |
| `agent_needs_you` | a pane starts waiting for an approval (`blocked`) or for the answer to the agent's question (`waiting`) |

Rules: a phone that is connected right now is not pushed (it sees the change live), and one that disconnected is; at most one push per pane and kind every 30 s, so an agent chaining turns is one piece of news; a pane that never worked here (a replay, a daemon that took over) says nothing; a subagent finishing never finishes its parent's pane, so it never pushes, while a subagent's approval prompt (which holds the parent turn) is an `agent_needs_you`; crewmate panes keep their own pushes (`task_done`, `needs_you`). Revoking a phone removes its tokens; a token the relay refuses (`403`, `410`) is dropped. The payload is `{kind, pane, title}` where `title` is `<agent> · <project folder>` (at most 60 characters): never the prompt, the reply, the transcript or the session title. The relay copies those three keys into the FCM data and shows `<title>: An agent finished` or `needs you`; it accepts the two agent kinds only with a pane. **Tapping** the push opens that agent's chat: the app asks each paired Mac for `agent_status_all`, takes the one that has the pane and opens it over the current tab (nothing opens if the agent has since gone away). The app has no in-app notification settings; use the OS notification settings for Atlas. The relay must be deployed with the two new kinds before pushes arrive: an older relay answers `400` to them and hostd keeps the token.

#### Bringing push up

Push has never been switched on (see the status above): the relay is not deployed (`push.codeatlas.com.br` has no DNS record) and the app is built without Firebase config. Two scripts do it, in this order; each takes `--dry-run`, which prints every command and needs no login.

1. **Logins** (you, once; the scripts store none of them): `gcloud auth login` (an owner of the Firebase/GCP project), `firebase login`, `gh auth login` (admin on `codeatlasdev/atlas`, to write environment secrets), and `CLOUDFLARE_API_TOKEN` in the environment with Zone DNS Edit and Zone Origin Rules Edit on `codeatlas.com.br`. A Firebase project must exist (Firebase console, **Add project**, or an existing GCP project with Firebase added); its id is `<project>` below.
2. **The relay**: `GCP_PROJECT=<project> bun run push:deploy` (run `bun run push:deploy --dry-run` first). It enables the APIs, creates the `push-relay` service account (only `roles/firebasecloudmessaging.admin`, the narrowest predefined role with `cloudmessaging.messages.create`, plus read access to its one secret), creates `RELAY_GRANT_KEY` in Secret Manager if absent (never printed, never rotated by the script), builds with Cloud Build, deploys Cloud Run in `southamerica-east1` (0 to 3 instances), points `push.codeatlas.com.br` at it through Cloudflare and ends with a smoke check: `POST /v1/register` answers `200` with a grant and `POST /v1/notify` with a bad grant answers `403`. Why Cloudflare and not a Cloud Run domain mapping: that feature is Preview, "not recommended for production", and not offered in `southamerica-east1`; the script makes a proxied CNAME to the service's `run.app` host and an Origin Rule that rewrites `Host` to it (Cloud Run routes by `Host`).
3. **The app's Firebase config**: `scripts/firebase-mobile-config.sh <project>` registers the Android and iOS apps (`br.com.codeatlas.atlas.mobile` and the Lab id `….mobile.lab`), downloads `google-services.json` and `GoogleService-Info.plist` into a temp dir and stores them as `GOOGLE_SERVICES_JSON` and `GOOGLE_SERVICE_INFO_PLIST` in the `mobile-beta` and `mobile-store` environments, then deletes them. They never touch the repo. The release lanes write the files only for the build and delete them (`write_firebase_config` in `fastlane/Fastfile`); without the secrets the app still builds, with no push.
4. **APNs key, by hand** (iOS only; Firebase has no CLI for it): [developer.apple.com](https://developer.apple.com/account/resources/authkeys/list) → Certificates, Identifiers & Profiles → Keys → **+** → name `Atlas APNs`, tick **Apple Push Notifications service (APNs)** → Continue → Register → **Download** the `.p8` (shown once) and note its Key ID; the Team ID is under Membership details. Then [Firebase console](https://console.firebase.google.com) → the project → ⚙ Project settings → **Cloud Messaging** → **Apple app configuration** → the app `br.com.codeatlas.atlas.mobile` → **APNs authentication key** → **Upload** → the `.p8`, the Key ID, the Team ID. Without it Android push works and iOS push never arrives.
5. **Rebuild the app**: push needs a build that has the config, so ship a release (`bun run mobile:release X.Y.Z`; testers get it first). A build made before step 3 has no push.
6. **Check it end to end with a real phone** (a simulator has no APNs): install the TestFlight or Play internal build, open it and allow notifications; pair a Mac, start an agent in a terminal there, send the app to the background (or lock the phone) and let the agent finish or ask for approval. The phone must buzz within seconds, and tapping the push opens that agent's chat. If it does not: `gcloud run services logs read push-relay --region southamerica-east1` (`403` means the phone's grant is stale, so reopen the app once; `502` is FCM, usually the APNs key or the role), and `curl -sS -X POST https://push.codeatlas.com.br/v1/register -d '{"token":"x"}'` must answer `200`.

## Lab lane (validate a branch without touching your install)

Validating a change to hostd or to the phone app used to mean replacing your installed Atlas and restarting your hostd in the middle of real work. The lab lane runs the branch **beside** your installation, on your real agents:

```bash
bun run mobile:lab                     # build, start the lab hostd, install Atlas Lab on your iPhone, print the pairing QR
bun run mobile:lab --device "<name>"   # a specific device (id or name)    --android | --sim: a physical Android phone, a booted simulator
bun run mobile:lab --watch             # + rebuild and restart the lab hostd on crates/ changes; `flutter run` (debug, hot reload) stays attached
bun run mobile:lab --status            # is the lab running, and what does it follow
bun run mobile:lab --stop              # stops the LAB hostd only
```

**The shadow hostd** (`atlas hostd --lab`, from `target/debug/atlas`; `--dir` overrides the folder) keeps every file under `~/.atlas/lab` (`$ATLAS_HOSTD_DIR/lab`): socket, pid, token, `mobile/key`, `devices.json`, invites and `audit.log`. It never writes under your real directory. It is a *client* of your real hostd's socket:

| It does | How |
|---|---|
| show your real agents | seeds from `agent_status_all` and follows `agent_status` / `agent_approval*` pushes into its own agent hub |
| run the branch's code | `agent_tree`, `agent_history` and `project_*` run in the lab over the same session files and project registry (read only) |
| act on your terminals | `pty_list`, `pty_read`, `pty_write`, `pty_signal`, `agent_send`, `agent_interrupt`, `agent_approve`, `agent_launch` are forwarded to your hostd; a phone's terminal gets its own connection to it, relayed back, and released when the phone leaves |

It never starts the hook server (that would steal the endpoint your agents read), never adopts or hands off terminals, and refuses to create, kill or resize one. Your hostd holds a permission prompt only for *its own* phones, so an experimental phone never makes a real agent wait. If your hostd restarts (`atlas update`), forwarded calls fail with a clear message and the lab reconnects and re-seeds on its own; with no hostd at all it exits at start with an error. It has no idle timeout: it stops with `--stop`.

**Atlas Lab** is the same app built with `--dart-define=ATLAS_LAB=1 --dart-define=ATLAS_SHA=<git sha>` under its own identity: bundle id `br.com.codeatlas.atlas.mobile.lab` (iOS scheme `lab`, Android gradle property `atlas.lab=1` giving the id `….mobile.lab`), the name "Atlas Lab", an orange icon (`bun run mobile:lab:icons`, the phone twin of `icons:dev`) and a slim `LAB · <sha>` strip on top. Secure storage is isolated by the bundle id (no keychain or app group is shared), and the app has no push (no Firebase or APNs identity), so nothing in it depends on one. The lab pairs with its own code and key; your real app and its pairings are untouched. The real app's build, id, name, icon and output paths are unchanged.

Notes: build and install go through `scripts/heavy.sh`; the one-shot path is `flutter build` + `flutter install` (an attached `flutter run --release` hangs, so `--watch` attaches a debug run). A phone must be unlocked and trusted for `flutter install`. `atlas.yaml` action `M` runs it.

## Files

Under `~/.atlas/mobile/` (`$ATLAS_HOSTD_DIR/mobile/`): `key` (the computer's iroh identity, 0600), `devices.json` (paired phones and their permissions), `audit.log` (one JSON line per non-read request from a phone, with typed text logged as a length only). `ATLAS_MOBILE_RELAY=0` turns relays and address lookup off (LAN only).

## Building the app

Needs the Flutter version pinned in `apps/mobile/pubspec.yaml` (`environment.flutter`, always the newest stable; the gate fails with `flutter upgrade` when yours is older, see `apps/mobile/AGENTS.md`) and a Rust toolchain (the transport is the `apps/mobile/native` crate, bound through flutter_rust_bridge). `scripts/mobile-check.sh` (part of `bun run check`) runs `flutter analyze` and `flutter test`. It is skipped with a notice when Flutter is not installed.

## Goldens

Screenshot tests compare against `apps/mobile/test/goldens/<os>/`: Flutter draws text a few pixels differently on macOS and Linux, so each platform has its own recording and is compared exactly against it (`test/flutter_test_config.dart`). After a visual change, record both: `flutter test --update-goldens` on a Mac writes `macos/`; for `linux/`, push and take the images from the failed CI run's `mobile-golden-failures` artifact (each `<name>_testImage.png` becomes `linux/<name>.png`), or run `--update-goldens` on Linux. Check that the two sets show the same thing.

## End-to-end test (iOS Simulator, Android emulator)

`bun run mobile:e2e` (`scripts/mobile-e2e.ts`) runs `apps/mobile/integration_test/e2e_test.dart` against a real `atlas hostd`: the app pairs over iroh, lists a fixture project, opens it and a service's sheet, the Agents tab, an agent's chat and its terminal, whose replay must arrive. It touches nothing of yours and never shows a window:

- hostd runs in its own dir under `/tmp` with relays off (`ATLAS_MOBILE_RELAY=0`; the simulator shares the computer's network), with the fixture project and one agent terminal;
- the simulator is a dedicated `atlas-e2e` device, erased on every run (no pairing survives in its Keychain) and booted headless: Simulator.app is never opened.

It takes about two minutes, mostly the iOS build. `bun run mobile:watch` (`--watch`) is the one to look at: it opens Simulator.app on the test device once the app is built, pauses on each step and names it in a banner over the app (1/6 pairing … 6/6 the agent's terminal), the only option that shows a window; `--record <file.mov>` films the simulator screen instead, without showing anything. `--keep` leaves hostd, its dir and the simulator up for a look; `--device "<model>"` picks the simulator model (default iPhone 15 Pro). macOS with Xcode only; it is not part of `bun run check`.

Android: `bun run mobile:e2e:android` / `bun run mobile:watch:android` (`--android`) run the same test on a dedicated `atlas-e2e` emulator (its AVD is created from the newest complete arm64 Google APIs image; your own AVDs are never touched), wiped each run and started without a window unless watching (an emulator cannot be shown after a headless start, so `--watch` shows it from the beginning). It reaches the computer's loopback as `10.0.2.2`. Needs the Android SDK and the Rust Android targets (`rustup target add aarch64-linux-android armv7-linux-androideabi x86_64-linux-android i686-linux-android`). `flutter test` gets `--timeout 5m`, so a stuck step fails with a message.

## Releases (testers, then the stores)

Shipping an update, step by step:

1. Merge the app's changes into `main` (nothing is published).
2. `git checkout main && git pull`.
3. `bun run mobile:release 1.0.1`: a fix bumps the last number, new features the middle one, a big change the first.
4. About 20 minutes later testers have it in TestFlight and Play internal testing (Actions → **Mobile release** shows the run).
5. Try it on a phone.
6. Good: in that run, **Review deployments** → `mobile-store` → **Approve and deploy**. Not good: do not approve; fix, merge and release the next version.
7. Apple reviews (usually 1 to 2 days) and releases on approval; Google reviews and publishes. A store that rejects says why by email; the rejected version never reaches the public.

How it works:

One path, one tag: `bun run mobile:release 1.2.0` (on an up-to-date `main`, clean tree; `--dry-run` prints what it would do) tags `mobile-v1.2.0` and pushes the tag. It refuses a malformed version, an existing tag or one lower than the last mobile release. The tag runs the `Mobile release` workflow (`.github/workflows/mobile-release.yml`, fastlane `apps/mobile/fastlane/Fastfile`):

0. **CI gate:** nothing is built until CI (`ci.yml`) has passed on the tagged commit (`scripts/ci-passed.sh`, the same gate as the desktop and CLI release). A tag on a red or still-running commit waits up to 2 hours for that run and then uploads nothing.
1. **Unattended:** it builds version `1.2.0` (from the tag; `mobile-vX.Y.Z` only) with one build number for both stores, and uploads it to **TestFlight** and the **Play internal testing** track.
2. **After your approval:** the `store` job waits on the `mobile-store` environment. Its required reviewers approve it from the run (**Review deployments**). It then promotes that same build, never a new one: `fastlane ios_release` submits it to App Store review and Apple releases it as soon as it is approved; `fastlane android_release` moves it from internal testing to production, to every user at once. Not approved within 30 days, the run expires and the version stays with testers. A fix is the next tag (`mobile-v1.2.1`).

Commits and pull requests never publish anything. A run started by hand (Actions, **Run workflow**) builds for testers only and keeps `pubspec.yaml`'s version. Locally, `bun run mobile:beta` does step 1, and `BUILD_NUMBER=<n> VERSION=1.2.0 bundle exec fastlane release` step 2. Nothing secret is in the repo: the lanes read the environment; CI reads the secrets of the `mobile-beta` environment (step 1) and of `mobile-store` (step 2: the App Store Connect key and the Play service account).

Set up once in GitHub: environment `mobile-store` with **Required reviewers** (the maintainers) and **Deployment tags** limited to `mobile-v*`; its secrets `ASC_KEY_ID`, `ASC_ISSUER_ID`, `ASC_KEY_P8`, `PLAY_SERVICE_ACCOUNT_JSON`. Store texts, screenshots, the privacy answers and the age rating are kept in each store's console for now.

| Variable                                                                                            | What                                                                                                                                                                                       |
| --------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `ASC_KEY_ID`, `ASC_ISSUER_ID`, `ASC_KEY_P8`                                                         | App Store Connect API key (role **App Manager**; the `.p8` contents). It uploads the build and signs it (automatic signing, no certificates to manage).                                    |
| `APPLE_TEAM_ID`                                                                                     | The team the app is signed for.                                                                                                                                                            |
| `TESTFLIGHT_GROUPS`                                                                                 | Optional (a CI variable, not a secret): internal TestFlight groups to hand the build to, comma-separated. External testers need Apple's beta review.                                       |
| `PLAY_SERVICE_ACCOUNT_JSON`                                                                         | Google Play service account JSON, invited in Play Console with release rights on this app only.                                                                                            |
| `ANDROID_KEYSTORE_BASE64`, `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS`, `ANDROID_KEY_PASSWORD` | The Play upload key (`base64 -i upload.jks`). Locally, `android/key.properties` (git-ignored) works too; without either, a release build is signed with the debug key, which Play refuses. |
| `GOOGLE_SERVICES_JSON`                                                                              | `google-services.json` for Android Firebase push notifications, written by the Android build only while it runs. Set by `scripts/firebase-mobile-config.sh` ("Bringing push up"). Without it the app builds without push. |
| `GOOGLE_SERVICE_INFO_PLIST`                                                                         | `GoogleService-Info.plist` for iOS Firebase push notifications, written by the iOS build only while it runs. Set by `scripts/firebase-mobile-config.sh`. Without it the app builds without push.                          |

Once per store, by hand: create the app record (`br.com.codeatlas.atlas.mobile` on both; `br.com.codeatlas.atlas` is the desktop app), and upload the first Android bundle through Play Console (the API cannot create an app's first release). Testers: an internal TestFlight group (up to 100 team members, no review) and the Play internal testing list (up to 100 emails); each tester gets an invitation link.

### Store dashboards from an agent (optional)

To see and manage both stores without opening them (testers, build status, review state), a maintainer can add the [app-publish-mcp](https://github.com/mikusnuz/app-publish-mcp) server to their agent. It was read at commit `9d52fb86` (v0.7.0): no telemetry or install scripts; it talks only to `api.appstoreconnect.apple.com` and Google's APIs. Conditions: pin that version (`npx -y app-publish-mcp@0.7.0`); use a dedicated App Store Connect key with the **App Manager** role and a Play service account limited to this app; set every variable in the MCP config (it also reads a `.env` from its working folder); start with `APP_PUBLISH_READ_ONLY=true`. Read-only only hides write tools from the agent, and the report tools can still write files. Without it the agent can submit for review, release to production or delete testers. Keys stay on the maintainer's machine, never in this repo.
