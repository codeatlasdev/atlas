# Atlas Mobile

Atlas Mobile (`apps/mobile`, iOS and Android, preview) is a remote control for the Atlas running on your computer. There is no account and no Atlas server: the phone connects straight to `atlas hostd` on your computer over [iroh](https://www.iroh.computer) (QUIC dialed by public key). It goes direct when the network allows and otherwise through n0's public relays. Traffic is end-to-end encrypted either way, and a relay can't read it.

It works while the Atlas window is closed, because hostd keeps running: it only exits by itself when nothing runs, nobody is connected and no phone is paired, so a paired phone keeps it up (revoke the phone and it goes back to leaving after 10 quiet minutes). The computer has to be awake.

## Pairing

1. On your computer: **Settings → Integrations → Mobile**. The pair card lists the three steps (get Atlas Mobile, open it and tap **Scan pairing code**, scan the code); **Show pairing code** makes a QR and a 6-digit code that work once, for two minutes, with a countdown bar. When it runs out the card says **Code expired** and **New code** makes another.
2. In Atlas Mobile: on first launch **Scan pairing code**; later **Settings → Computers → Pair another computer** (**Pair a computer** while none is paired). Then scan the code (or **Paste link**, after **Copy link** on the card).

The phone does not need to be on the same Wi-Fi: it connects through an encrypted relay, or straight to the computer when both are on one network. The computer must stay awake with Atlas running. The card's **Pairing doesn't work?** folds those two notes and the VPN one below. Until Atlas Mobile has a public store listing the card links this page ("still in testing"); the store URLs belong in one constant, `MOBILE_APP` in `apps/desktop/src/lib/settings/mobile.ts`.

The code works once. Five wrong attempts cancel it. After pairing, the phone is recognised by its own key, and it appears under **Paired phones** by itself while the code is on screen (the pane reads the list every second then, and every 5 s otherwise).

Each paired phone is one row: **Phone A3F9** (the app sends the same name, "Atlas Mobile", for every phone, so the pane titles an unnamed phone by the start of its key; **Rename** gives it a name of your own, kept in `devices.json`), a status line (**Connected now**, or **Last seen 3 min ago**, then the pairing date in your locale), a one-line summary of its access (**Full access**, **View only**, **Custom: 3 of 5**) and **Rename**, **Activity** and **Unpair** in the row's header. **Activity** lists what the phone changed lately, read from `audit.log` (typed text only as a length). **Edit permissions** folds out the five permissions in a View group and a Control group, each with what granting it risks:

| Permission                                  | Allows                                                                                                                                              |
| ------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| See projects, logs and agents               | project and service state, logs and search, agent tabs and replies, terminal list, a project's changed files and their diffs (`git_status`, `git_diff`); read the images of a crewmate's task, its audit and usage |
| Restart services, run actions, send prompts | restart/start/stop a service, start or stop a stack, run an action (its confirm step is shown on the phone), send a prompt to an agent that is idle or done, open a new terminal (`pty_open`), stage and unstage files, commit (with the AI message), push and open a pull request (`git_stage`, `git_unstage`, `git_commit`, `git_commit_message`, `git_push`, `git_pr_create`); send a task, with images, to a crewmate (uploading an image is the same permission); answer a crewmate's question (`crewmate_answer`) or a card, including a secret it asks for (Face ID first) |
| Answer agent permission prompts             | allow or deny a Claude Code / Codex tool call                                                                                                       |
| Watch terminals                             | live terminal output                                                                                                                                |
| Type in terminals                           | keystrokes; the app also asks for Face ID / biometrics before each session                                                                          |

**Unpair** (it asks first; the host command is still `mobile_revoke`) cuts the phone off immediately and forgets it, and takes its push tokens with it: on this computer, and on every crew server behind it (the Mac sends each one `push_forget` with the phone's node id; a crew server that is unreachable at that moment keeps the phone on a list saved on the Mac, `mobile/pending-forget.json`, and gets the `push_forget` the next time it connects, also after a Mac restart; a server removed from the desktop's registry drops off the list; the phone is cut off from the Mac either way). A token the phone registered on a crew server through the Mac is stored there under the phone's own node id (the Mac stamps it from the phone's connection; whatever the phone puts in `node` is overwritten), so revoking the phone on the crew server itself clears it too. A phone can never run shell commands through `exec`, read or write files, change its own permissions or manage devices.

**No computer at hand?** Under the scanner, **No computer at hand? Explore a demo** opens a computer that lives in the app (`apps/mobile/lib/core/demo/demo_computer.dart`): sample projects, services, logs, agents with a permission prompt to answer, a crew. It answers the same protocol as hostd, connects to nothing and is not saved; **Leave demo** (Settings → Computers, in the ⋯ menu of the demo computer), pairing a real computer or relaunching ends it. It is how App Review and Play review use the app (their review notes point to it), and the tests run every screen against it.

### Pairing fails with a VPN or WARP on

The pairing code carries this computer's key, its relay and its direct addresses (`addrs`). hostd publishes only the addresses of real LAN interfaces, private IPv4 first, then ULA and global IPv6. It leaves out loopback, link-local (`fe80::`, `169.254.`), CGNAT `100.64.0.0/10` and any address that only a tunnel owns (a `utun`/`tun`/`wg`/`tailscale` interface, or any interface flagged point-to-point), because a phone on the LAN cannot reach those (`crates/atlas-host/src/mobile/addrs.rs`, #113). If every address is a tunnel's, they are published anyway rather than an empty list; the relay still connects.

What this does **not** settle: whether a phone on the same Wi-Fi reaches the computer's LAN address while a full-tunnel VPN is on. Packets from the phone arrive on `en0`, but the replies leave by the route the VPN installed; a VPN that captures the default route (WARP in its default mode) can send them into the tunnel, so the direct path never completes. That depends on the VPN's routing and split-tunnel rules and needs a phone on the network to check. Until it is measured, expect the relay (`ATLAS_MOBILE_RELAY` unset) to carry the connection, and if pairing does not complete:

1. Make sure `ATLAS_MOBILE_RELAY=0` is **not** set (it turns the relay off, so only the LAN addresses remain).
2. Pause the VPN, or add the LAN (`192.168.0.0/16`, your Wi-Fi subnet) to its split-tunnel exclusions, then pair again.
3. Check what is published: Settings → Integrations → Mobile lists the addresses in the pairing link under **Pairing doesn't work?** while a code is showing (`addr=` parameters).

### The app and the computer disagree on the protocol

On every connect the phone asks hostd's `info` once and compares its `proto` with the two constants in `apps/mobile/lib/core/protocol/protocol_version.dart`: `kAppProto` (what this app speaks, mirrors `PROTO` in `crates/atlas-host/src/protocol.rs`) and `kMinHostProto` (the oldest hostd it works with). Bump `PROTO` and `kAppProto` together on any non-additive wire change (a renamed or removed command or field, a changed meaning); a new command or an optional field is additive and needs no bump. Raise `kMinHostProto` only when the app starts to need something an older hostd lacks.

- **hostd older than the app** (`proto` below `kMinHostProto`, or no `proto` at all, which is protocol 1): the home screen says **Update Atlas on <computer>** and to run `atlas update` there; the Crew tab and a crewmate's chat show the same one line. Nothing else is asked of that computer, so there is no `bad request` per command.
- **hostd newer than the app**: only when its `info` carries `min_client_proto` above `kAppProto` (hostd does not send it today): **Update Atlas Mobile**. Without that field a newer hostd is assumed additive.

A mismatch is not an outage, so the phone does not retry it in a loop: it checks again when the app comes to the foreground, on pull to refresh and on **Try again**, and the state clears as soon as the versions agree.

### How a screen says what is going on

One path for the connection and one for the states, so a new screen does not invent either:

- **Getting a connection:** `requireMux(ref, device)` in a provider, `requireMuxOf(ref, device)` in a widget handler (`lib/core/connection/require_mux.dart`). Both wait while the link opens and return the live connection, or throw `DeviceOffline` (the computer is off) or `DeviceProtocolMismatch` (the section above). `errorText(e)` turns a caught error into the one sentence to show. A background refresh that must not wait uses `liveMux(ref, device)` and skips when it is null.
- **Rendering an `AsyncValue`:** `AsyncView` (`lib/core/ui/async_view.dart`) draws loading (the one spinner), the error with **Try again**, the empty state, the offline state and the protocol-mismatch state; the screen only supplies the data builder and the copy. A list that reads `value ?? []` shows "empty" while it is still loading: never do that.
- **A computer that is not connected:** `ReachingView` (full screen: reaching, can't reach, or the update message) and `OfflineStrip` (one line over a screen that keeps showing history). `test/goldens/<os>/async_view_states.png` pins the set.

## Projects on the home screen

`project_list` answers `{projects: [...]}`, one entry per project of the desktop's registry (`<hostd dir>/desktop/projects.json`; SSH checkouts are skipped, the desktop owns them), in registry order. Each entry has `id`, `root`, `name`, `running`, `services` and `agents`, plus what the phone needs to group and filter. All of it is read from files (the list is polled every 5 seconds for every entry, so there is no `git` process):

| Field | Meaning |
| --- | --- |
| `kind` | `"project"` when the root has an `atlas.yaml`/`atlas.yml` or is a git checkout (a `.git` directory or file at the root), else `"folder"` (a folder opened once, like `~/Downloads`) |
| `repo` | the main repository's root: a main checkout's own root, or for a linked worktree the root of the checkout it was added from; `null` when the folder is not a git checkout |
| `branch` | the checkout's HEAD branch; `null` when detached or not git |
| `worktree` | `true` for a linked worktree (its `.git` is a file pointing at `<main>/.git/worktrees/<name>`), so the phone can fold worktrees under `repo` |
| `pinned` | the registry entry's pin (`false` when unset) |

Entries whose folder no longer exists on disk are left out. The stacks of the entries are asked concurrently.

`project_service {id, op, service?}`: `op` is `restart`, `start` or `stop` for one `service` (required), `up` to start the stack detached, or `down` to stop the whole stack (the desktop's **Stop**; `service` is not used). `down` on a stack that is not running answers `{}` as well; if the stack is still alive 10 seconds after the shutdown request, it fails with a message saying it is still stopping.

## Review and ship from the phone

A project's page has **Review changes**: the changed files (staged and not), the diff of each (the same code block the chat uses, `diff` mode), a stage toggle per file, **Commit** (type a message or **Write with AI**, which runs the agent CLI of Settings → Git on the staged diff exactly as the desktop does: secrets withheld, lockfiles named), **Push** and **Open a pull request** (`gh pr create`). It is a fixed set of hostd commands, never a git command line: `root` must be a registered project or one of its worktrees (compared after canonicalization), paths must be relative and stay inside it (a symlink out is refused), the commit message goes on stdin, a push is never forced and only sends the current branch (`--set-upstream origin` the first time). Reading needs the first permission; everything that changes a repo or reaches GitHub needs the second. The audit log records the call but only the length of the message, title and body. hostd does the work itself (`crates/atlas-host/src/git.rs`, parsers and the commit-message logic shared with the desktop in `atlas_core::git_review`), so it works with the Atlas window closed; `gh` must be signed in on the computer.

## Approvals

Claude Code and Codex run `atlas hook … permission-request` before showing their own prompt. While a phone is connected, hostd shows the prompt on the phone and waits up to 55 s for Allow or Deny. With no phone connected, it answers nothing at once, and the agent asks in the terminal as usual. Re-run `atlas setup claude-code --apply` / `atlas setup codex --apply` once so the hook is registered with its 60 s timeout. omp approvals are shown as "needs you" but answered on the computer.

### Permission modes of a crewmate

A crewmate has a permission mode, **Ask**, **Accept edits** or **Bypass**, that hostd applies to every tool call ([Atlas Crew](crew.md)). The phone shows it wherever the crewmate appears and switches it (`crewmate_set_approval`, the `approve` scope: a phone paired without it says so). The mode is a pill under the header of the chat (lock, pencil or shield; amber only for Bypass), a line on every row of the Crew tab and a row in the profile; one tap opens a sheet with the three modes, and a switch while the crewmate works says it applies from the next tool call. It follows `crewmate_updated`, so a change made on the desktop or in Telegram shows at once. A crewmate on an engine with no approval channel (Codex, OpenCode) shows its mode fixed, with the reason. Bypass is left out of every choice when the crew does not allow it (Crew settings → Permissions: the default mode for new crewmates and **Allow Bypass on this crew**), and hostd's coded refusals (`crew.approval.bypass_disabled`, `unsupported_engine`, `forbidden`) are said in the app's language.

A tool prompt is answered in one tap: **Allow once** (the primary), **Allow for this task** (the same kind of call until the task ends) or **Deny**; *Comment or more options* opens a sheet with a comment the agent receives with the answer. A call a rail held (protected paths, tasks that never auto-run) is shown with why and can only be allowed once. There is no "always".

## Agents on the phone

An agent's chat is read from its session file (`agent_history`, `crates/atlas-host/src/agents/history.rs`): omp, Claude Code and Codex transcripts become one timeline of turns, thinking, tool steps (intent, status, clipped output) and, for omp, the subagents a `task` call started, each read from `<session>/<Name>.jsonl` (the phone names a subagent, never a path). omp subagents load the status extension in the parent's terminal; hostd recognizes their session files under the parent's session dir and never lets them rename, retarget or finish the pane (an approval still blocks it). The title is omp's session title (the `title` slot, else the session header's, else the first thing the user typed, one line: never an injected block and never a subagent's assignment). **The tree** (`agent_tree`, `crates/atlas-host/src/agents/tree.rs`) lists the agent and every subagent, however deep, as flat nodes `{id, parent, name, agent, model, status, task, duration_ms, tokens, cost, tool_count, now, report, updated_at, agent_type, thinking, requests, active_ms, context_tokens, context_window, recent}` (the root is `id: ""`, and also carries `todos`). omp ids are the dotted names omp uses on disk (`Scout`, `Scout.Deep`: `<session>/Scout/Scout.Deep.jsonl`); Claude Code's are `agent-<id>` from `<session>/subagents/`; Codex has none, so its tree is the root alone. `status` is `pending|running|completed|failed|aborted|idle`: the parent transcript's `async-result` (`<task-result status=…>`) decides how a subagent ended; before it, `running` while its lock file (`.<Name>.jsonl.lock.os`) exists or its transcript changed in the last minute, `completed` once `<Name>.md` exists, else its last `stopReason` (`error` → failed, `aborted` → aborted), else `pending`. `now` is the intent (or `tool: detail`) of the node's open tool call; tokens and cost are summed from the node's own transcript. The rest feeds the hub, all from that same transcript: `agent_type` (omp's agent definition, `task`/`scout`; null on the root), `thinking` (last `thinking_level_change`), `requests` (assistant messages), `active_ms` (time between consecutive entries, gaps over 5 minutes counted as parked), `context_tokens` (the last request's prompt: input + cache read + cache write), `recent` (the last 8 tool calls, `{at, tool, intent, status: running|ok|error}`). `context_window` is only what omp itself reported in the parent's `task` result (`details.progress[].contextWindow`, present for synchronous spawns); hostd never guesses a window from the model name, so an agent without one shows no context bar. The root's `todos` is `{phases: [{name, tasks: [{content, status}]}], done, total}` from omp's latest todo state: the last `user_todo_edit` entry or successful non-`view` `todo` result in the transcript (the same rule `todo-tracker.ts` rehydrates by); other agents have `null`. `agent_history` takes a dotted `sub` (every segment `[A-Za-z0-9_-]`, never a path) and also returns `result` items (a subagent finished) and `compaction` items. What omp injects as a *user* turn is not one: `<irc from="parent" agent="Main">…</irc>` (behind the `[Wait interrupted by message]` marker or not) becomes `{kind: irc, from, agent, text}`, a `<system-notice>`/`<system-injection>`/`<system-reminder>` block `{kind: notice, text}`, and omp's `advisor` message one `{kind: advisor, severity, text}` per note (`blocker`, `concern`, `nit`…). `messages` for older phones keeps typed user turns only. **Steering**: `agent_send` with `steer: true` types into a *working* omp agent, which queues it for the running turn; Claude Code and Codex, and omp without `steer`, still refuse while the agent works. Stop sends Escape (`agent_interrupt`, only while the agent works); slash commands are typed like any message. **New agent** (`agent_launch`) asks Atlas Desktop over `~/.atlas/desktop.sock` for `terminal_create` in the project, so it needs the desktop running. Both need the **act** permission.

**The hub on the phone** (`apps/mobile/lib/features/agents/agent_hub_screen.dart`) is omp's Agent Hub: the app-bar button opens the roster of the pane's agents (a long-press on a crew chip opens that agent's detail directly) with `N running · M parked`, the totals (cost, active time, requests, tools, tokens), a **Flat / By parent** switch (the tree indents; flat names `↳ parent` on each row) and **All / Running / Done / Failed** filters (each with its count). A row is the status ring, the dotted name, type · model · thinking, the task in one line and its numbers with the last activity. Tapping it opens the **detail**: Task, Current (the running tool), Usage with the context bar (`292K/1M 29%`, only when omp reported a window), Lineage (spawned by, children: each a link that opens that agent's detail), the todos for the main agent, Recent activity (timestamped tool rows with their outcome) and the report. Its buttons stay pinned under the scrolling content: **Open conversation**, **Back to Main** (or **Back to <parent>** on a deeper agent) and **Message**. In the chat, a persistent breadcrumb (`Main › Scout › Deep`, every crumb a chip, `Main` first) is on screen while a subagent is focused. The main agent shows a **Waiting on N jobs** strip (running subagents, a tiny bar of each one's context use, each a link) and a collapsible **todo card**; IRC, notice and advisor items render as compact cards (advisor by severity: blocker red, concern amber), never as the user's bubbles. hostd can only type into the main agent's terminal, so a message written while a subagent is focused is labelled *Message Main about <name>* and sent to the main agent as `Tell <id>: …` (as a steer while it works); only omp relays it, so Claude Code and Codex show no composer on a subagent. Claude Code and Codex degrade to what they have: a Claude agent's subagents list flat, a Codex agent is the root alone.

### Worktrees and agents in a worktree

The phone lists, creates and removes git worktrees of a project and starts an agent in a chosen one, **with the desktop app closed**: hostd does it itself (an agent launch goes to the desktop's tab when the app is running) (`crates/atlas-host/src/worktrees/`). The desktop uses the same code and the same registry file (`~/.atlas/desktop/projects.json`, edited under a cross-process lock), so both see the same worktrees, in the same folders (`<workspaceDir>/<repo>/<name>`), with the same branch rules, port offsets and `worktree:` hooks of `atlas.yaml` (`shared`, `seed`, `setup`, `archive`).

| Command | Scope | Does |
|---|---|---|
| `worktree_list {project}` | `read` | the repo and its worktrees (`id`, `path`, `branch`, `main`, `dirty`, `portOffset`), git read live |
| `worktree_create {project, name?, base?}` | `act` | `name` is slugged (empty picks a sea name), `base` must be an existing ref (never an option); `setup` runs headless and its result comes back, a failing setup keeps the checkout |
| `worktree_remove {id}` | `act` | only when nothing would be lost, the desktop's auto clean-up rule: answers `{kept: "dirty" \| "secrets" \| "unpushed"}` otherwise. Never forced, the branch stays. A main checkout is refused |
| `agent_launch {project, agent, prompt?, worktree?}` | `act` | with Atlas Desktop running it opens a real tab there (`terminal_create` on the desktop's control socket, with the worktree's folder); with the app closed (nothing listens on the socket) hostd spawns the agent itself in that folder, never with the agent's yolo flags. A desktop that answers with an error is not "closed": the error is returned, nothing is started behind its back. The project's main checkout without `worktree` |

All of them take registry ids, never paths, and ignore SSH checkouts (the desktop owns those). The lab hostd forwards `worktree_create`, `worktree_remove` and `agent_launch` to your real hostd and answers `worktree_list` itself.

### A new terminal from the phone

With no computer at hand you can still run a command: a project's page (Agents tab, **New terminal**) and the computer's page (Projects header, **New terminal**) start a shell on that computer and open it in the terminal screen, with the desktop closed (`crates/atlas-host/src/mobile/shell.rs`). hostd starts the user's login shell, the same default every desktop tab gets from `Session::spawn` (an empty `argv`: `$SHELL -l` on Unix, PowerShell or `cmd` on Windows), and the terminal is an ordinary hostd pty with no pane key, so a desktop that opens later lists it with the others.

| Command | Scope | Does |
|---|---|---|
| `pty_open {project?, worktree?, crewmate?}` | `act` | `{pty}` of a new shell. Attaching (`pty_attach`) needs `term_read`; typing still needs `term_write` and the app's Face ID / passcode gate, exactly as for any terminal |

The phone sends ids, never a path or a program (`pty_create`, which takes any folder and argv, stays refused). On a **computer**, `project` is a registry id of `project_list` and `worktree`, when given, must be one of **that project's** worktrees (`worktree_list`); a path, a `..`, an unknown id, another project's worktree and a request with no project are all refused and start nothing. On a **crew server** (`ATLAS_CREW_HOST`), which has no projects: no argument opens the crew home (the crew user's `$HOME`, as the sign-in terminal does), and `crewmate` opens that crewmate's work tree (`crew/<id>/work`, or its project checkout), found by listing the crew store, so an id that escapes it is simply unknown; a crewmate that has not run a task yet has no work tree and is refused with that reason. Both run as hostd's own user (on a crew server the crew user, never root).

The audit log (`audit.log`) records `pty_created {project, worktree, crewmate, cwd}` under the phone's node id once the shell exists (the folder hostd resolved, so what was asked and where it went can be compared), next to the request line itself; what is typed afterwards is logged as a length only, as before.

A crew server reached **through a Mac** is not offered the button: a terminal's output streams to the connection that attached it, which would be the Mac's relay, not the phone (the same limit as the engine sign-in), so `pty_open` is refused inside `crew_call`. Pair the phone with the crew server itself to open a terminal there. The reply is read from hostd's real payload (`apps/mobile/test/fixtures/pty_open.json`, written by `UPDATE_FIXTURES=1 cargo test -p atlas-host --lib -- mobile::tests::a_phone_opens_a_shell`). `pty_open` is a new command with optional arguments: additive, no `PROTO` bump.

## Crew on the phone

Crewmates live on crew servers (`atlas crew install`, see [Atlas Crew](crew.md)). A phone reaches one of two ways. **Directly:** the phone is paired with the crew server itself (its own iroh identity, the same pairing as a Mac), so the crew works with every other computer off. **Through a Mac:** Atlas Desktop reaches the server over SSH and the phone talks to its paired Macs, which relay. The Mac's hostd relays: `crew_servers` lists the crew servers in `~/.atlas/desktop/crew-servers.json`, and `crew_call {server, cmd, args}` runs a command there through hostd's own SSH connection to it (`$HOME` and the token read over `ssh`, then `ssh -N -L` to its `hostd.sock`, like the desktop; `crates/atlas-host/src/crew/relay/`). The crew server's pushes come back as `{"ev":"crew_event","server":…,"event":…}`. A relayed command needs the scope it would need sent to the Mac (`mobile::required_scope`); terminals and secrets are never relayed, and a relayed push passes the phone's scopes like the push inside. The phone shows each crew server as its own computer behind the Mac (`CrewTransport`, `crewDevicesProvider`). The Mac must reach the crew server with this user's SSH key (`BatchMode`, no prompt). macOS and Linux only.

### Pair a crew server with no computer in the loop

```bash
atlas crew pair user@server            # a QR code, a 6-digit code and the link; --port N for an SSH port other than 22
```

From any machine that can SSH to the server (a laptop, a tablet with an SSH app), `atlas crew pair` asks the crew server's own hostd for an invite as the crew user (`atlas hostd --mobile-pair` on the server: the same `mobile_pair_start` the desktop uses, one code, 120 seconds, five wrong tries), waits for the relay address so the link works off the LAN, and prints the QR (black on white, whatever the terminal theme) with the code and the link. In Atlas Mobile: **Settings → Computers → Pair another computer**, scan it. The phone pairs with the crew server directly and keeps it in its list of paired computers, so it is listed with no Mac on. Pair as many phones as you like, one invite each.

**Invites that were missed.** The desktop's **Add crew server** also pushes an invite to your phones (`computer_invite`), and stores it on the computer for the life of its code (`mobile_invites`, `read`). The phone now asks every computer it reaches for its pending invites when it connects, so one made while the phone was off or out of range shows up in the Crew tab as **New crew server**. An invite lives as long as its code (120 seconds) and is dropped when a newer code replaces it (a second pairing started), since its link would answer "bad code".

### Questions from a crewmate (`ask_user`)

An agent that cannot go on without an answer asks (`ask_user`) and waits up to 30 minutes. The question is on the task (`ask`: `id`, `question`, `options` with `key`/`title`/`subtitle`, `allow_text`), so the thread shows a card with the question, one button per option and, when the agent allows free text, a field. Tapping an option sends `crewmate_answer {id, ask_id, key}`, typing sends `{id, ask_id, text}` (`act`); the agent's call returns the answer and the card closes with the task's next push. hostd refuses an answer to an ask that is closed or unknown, and the card keeps the question with that message. The card reads the task exactly as hostd serializes it (fixture `apps/mobile/test/fixtures/crewmate_task_ask.json`, written by `ask_user_fixtures_are_real_payloads_and_the_phones_answer_wakes_the_agent`).

### Images on a task

The composer has an image button (**Attach image**): **Take photo** (camera) or **Photo library**, up to 4 images of at most 5 MiB (png, jpeg, webp, gif by their bytes; anything else is refused with its name before it is uploaded). Photos are scaled to at most 2048 px and re-encoded at 85 % quality first, so a camera shot fits the cap. The pending images show above the field with a remove button; **Send** needs text (a task is a prompt) and keeps text and images with the server's reason on screen when the task is refused. `image_picker` asks for camera access only when you take a photo, and the photo library through the system picker; the iOS usage strings say so.

In the thread, a task's images show right-aligned under its prompt, fetched from the crew server when they first appear and kept for the session (tap one to see it large). They travel through the Mac's `crew_call` like every other crew command, in pieces of at most 512 KiB (a protocol line is at most 1 MiB): `crewmate_attachment_put` (needs `act`) uploads, `crewmate_attachment` (needs `read`) fetches. A phone granted `act` but not `read` can send an image and then sees it as "Tap to retry" with `forbidden: read`; the rest of the thread is unaffected. The push relay never sees an image. The demo computer answers both commands and enforces the same caps, so the screens run against it.

A task that waits on a card the owner decides (Atlas's guards refused it, or a [UI task](crew.md#ui-tasks-and-proof) finished without two captures of its own) shows the captures the agent took as thumbnails (tap to enlarge) with the reasons on its card in the chat, and the Crew tab's **Captain's call** lists it with the same captures and **Retry** / **Override** in place (`crewmate_action_answer`, scope `act`; the list reads it from `crewmate_list.waiting_task`, scope `read`). In the chat card, **Add a screenshot** (camera or library) attaches a marked screenshot to the retry: it goes up like a task's images, is stored on the task as yours and staged for the agent; images with an override are refused. A task you send can be marked `ui` (`crewmate_task {ui}`); the agent's captures also show under its reply once it is done. The demo computer raises a `prove_ui` card for a task sent with `ui` and answers both answers, so the screens run against it.

### Dictation (speak instead of type)

The composer of a crewmate's chat has a **mic** next to the field when the crew allows voice (`crew_voice_status.enabled`, the owner's crew-wide switch; an older hostd, or one that refuses the read, shows no mic). Speech is recognised **on the phone**: the audio never goes to hostd, to the crew server or to the push relay. hostd learns only that the task was dictated (`crewmate_task.dictated: true`, which makes it tell the agent to expect homophones in identifiers and file names; the line is never shown as your text).

- **Tap to start, check or X.** Tapping the mic replaces the composer with a bar: **X** (discard), the words so far, the engine's name and a **check** (insert). The words the recognizer has heard are drawn **dimmed**, at the place they would land; they are not in the message until the check, which puts them at the cursor, or over the selection, with the spaces fixed (never glued to a word, never a doubled space; punctuation attaches to the word before it). **X** gives back the message as it was. Dictating never sends: **Send** is the same button as for typing.
- **Limits.** After 5 minutes (hostd's own cap) it stops by itself and **keeps what was said**: the bar says *Microphone off* and waits for the check or the X. The same happens when the engine ends, when a call takes the microphone and when the app goes to the background (the microphone is released at once, not when the app returns). Leaving the chat, or the crew switching voice off, releases it too.
- **Which engine, always shown.** *On this iPhone* (iOS 26+: `SpeechAnalyzer`; older iOS: `SFSpeechRecognizer` with `requiresOnDeviceRecognition`), *Android on-device* (Android 12+: `SpeechRecognizer.createOnDeviceSpeechRecognizer`), or *System recognizer (online)*. The language is the app's (pt-BR for Portuguese, en-US otherwise).
- **No silent fallback.** A phone with no on-device recognizer for the language (Android 11 and older, a language pack that is still downloading, a language Apple has no on-device model for) says so, and offers the system recognizer only as a **labelled opt-in**: *Use the system recognizer (online)*, *May send audio to Apple or Google*. The choice is per session; the next tap asks again. A phone with no recognizer at all gets the explanation and nothing to choose.
- **Why a native channel and not a plugin.** The promise is "on the phone", and `speech_to_text` 7.5 (read at its source) cannot keep it everywhere: on Android its `onDevice` flag uses `createOnDeviceSpeechRecognizer` only when `isOnDeviceRecognitionAvailable` says yes and otherwise falls back, silently, to `createSpeechRecognizer` (the default service, which may use the network), and the caller is not told which one ran; on iOS it has no `SpeechAnalyzer` and owns the audio engine and a start sound. So `lib/core/voice/` has the seam (`DictationRecognizer`, `FakeDictation` in tests) and the channel (`platform_dictation.dart`, which documents the wire), and the native side is ours and small: `ios/Runner/Dictation.swift`, `android/.../DictationPlugin.kt`. An engine that cannot do the language on the phone reports `language`; it never retries on a server.
- **Permissions** ([Permissions](#permissions)): *Microphone* on both (iOS `NSMicrophoneUsageDescription`, Android `RECORD_AUDIO`, asked in the composer after a sheet that says why), and on iOS *Speech Recognition* (`NSSpeechRecognitionUsageDescription`) for every recognizer except `SpeechAnalyzer`, which needs only the microphone. Both usage strings are in English and Portuguese (`InfoPlist.strings`). A refusal is an explained state: what stops working, **Open Settings** (not for a device policy), nothing records.
- **Accessibility.** Mic, check and X are labelled; a red dot with *Listening* and *Microphone is on* is the live indicator (still, not pulsing, with reduced motion); start, stop, discard, insert, the cap and the background are announced; the engine line is read as *Recognizer: On this iPhone*. Every word is in the catalog (`i18n/messages/mobile_voice`).
- **Tests.** `dictation_core_test` (where the words land, the session's states, the channel's wire), `crew_dictation_test` (the composer with a fake recognizer: partial then final at the cursor and over a selection, X restores the draft, nothing sends by itself, the cap keeps the text, the background releases the mic, the unsupported phone gets the labelled opt-in only, permissions, announcements, reduced motion), `crew_voice_contract_test` (hostd's real `crew_voice.json`: voice off hides the mic, `dictated: true` on the task) and `crew_dictation_golden_test`. The recognizers themselves need a device; they are checked by hand on one, not in CI.

### Read replies aloud, and answer cards by voice

Two things on top of dictation, both on the phone's own engines. The wire is hostd's (#648): the phone sends **only what was heard**, hostd decides what it means.

- **Read replies aloud.** A speaker button in the chat header (**Read replies aloud**, off by default, kept on this phone only, hidden on a phone with no installed voice for the app's language). Turning it on also sets `spoken_replies: true` on that crewmate (`crewmate_update`, so the agent ends its reply with a short line for listening); turning it off silences the voice and leaves the crewmate's setting alone (other phones, and the crewmate's settings, own it). When a task finishes while the chat is open, the phone says `task.spoken` (hostd computes it: the agent's `spoken:` line, else the first sentences of the reply without code, paths and links; empty says nothing). The thread you open is history and is never read; two replies landing together are read oldest first. A reply that arrives while the app is in the background is not read.
- **The voice is the system's, on the phone.** iOS `AVSpeechSynthesizer` (the voice and rate of Settings → Accessibility → Spoken Content), Android `TextToSpeech` with an installed voice that does not need the network. A channel and not a plugin, for the same reason as dictation: the text of a reply must not be able to leave the phone (`lib/core/voice/speech.dart` is the seam, `platform_speech.dart` the wire, `ios/Runner/SpeechReader.swift` and `android/.../SpeechPlugin.kt` the engines). The language is the app's (pt-BR or en-US); a language with no installed voice is never spoken in another one.
- **It stops at once** on any tap on the chat (the tap still does what it was for), when a microphone opens (dictation or a voice answer; nothing is read while one is open, so the phone never hears itself) and when the app leaves the foreground. A **Speaking** pill (a speaker, never the red microphone dot) shows while it speaks and stops it when tapped; it is a live region for a screen reader.
- **Answer by voice.** A tool approval (the chat bubble and the Crew tab's Captain's call) and a `choose` card have **Answer by voice**. It uses the same on-device dictation (same permissions, engine always named, X to discard) and the check sends the transcript: `agent_approve_voice {pane, req, transcript, lang}` or `crewmate_action_answer_voice {id, task, transcript, lang}` (`lang` is `pt` for Portuguese, `en` otherwise). The app **never maps words to an allow**; it shows hostd's verdict: **allow** / **deny** / **choice** (hostd already answered; a snackbar says what), **comment** (the words were not a plain answer: nothing is decided, and the sheet opens with them in the note so the person confirms by tap), **needs a tap** (nothing decided, with the reason: the crewmate is in Bypass, a rail holds the call, the call is destructive, or the source is untrusted) and **unclear**. A verdict this app does not know reads as unclear, never as a decision. The button is only there when the crew allows voice.
- **Accessibility.** The switch is announced as a switch (*Read replies aloud*, on/off); the Speaking pill and the verdict line are live regions; Answer by voice says what to say (*Say allow or deny*, *Say the option's number or name*). Every word is in the catalog (`i18n/messages/mobile_voice`).
- **Tests.** `speech_core_test` (one voice, silence when a microphone opens or the app leaves, which finished tasks are spoken), `crew_voice_answers_test` (against hostd's real `crew_voice_answers.json` and fakes for the recognizer and the speech: every verdict, no allow without hostd's verdict, speech stops on tap, dictation and background, the toggle sets the crewmate flag) and `crew_voice_answers_golden_test`. The synthesizers themselves need a device and are checked by hand on one.

### Push notifications

**Status (checked 2026-11-14): in the code, not live.** Everything below ships: hostd's notifier (plain agents and crewmates), `push_register` with a relay grant, revoke clearing tokens, the app's registration and its Notifications row in Settings, and the two bring-up scripts. What is **not** done is switching it on: the relay is not deployed (`push.codeatlas.com.br` does not resolve, so `curl -X POST https://push.codeatlas.com.br/v1/register -d '{"token":"x"}'` fails with "could not resolve host"), and the apps are built without Firebase config (no `GOOGLE_SERVICES_JSON`/`GOOGLE_SERVICE_INFO_PLIST`, no APNs key). So today no phone receives a push, and nothing here has been seen working on a real phone. "Bringing push up" below is the exact list of what turns it on. Re-run that `curl` after step 2: when it answers `200`, update this paragraph.

The app gets a push for a crewmate's finished task or approval prompt, and for a plain agent on your Mac (omp, Claude Code, Codex in a terminal) that finished or needs you, only while it is not connected. Registration (`core/push/`): when Firebase is configured **and notifications are allowed** (the app never shows the notification prompt at launch: see [Permissions](#permissions)) the app takes its FCM token, asks the push relay for the token's **grant** (`POST /v1/register`, `ATLAS_PUSH_RELAY` dart-define, default `https://push.codeatlas.com.br`) and sends `push_register {token, platform:"fcm", grant}` to every connected computer that can notify: the paired Macs, whose `info` lists the `push` cap (every hostd from the plain-agent push change on), and the crew servers behind them (the `crew` cap). The demo computer is skipped, and a hostd older than the `push` cap is not asked. It does this again on every launch and reconnect and when FCM refreshes the token, so an old registration without a grant is replaced the first time the updated app opens. Without a grant the app registers nothing and retries on the next connect, and Settings → This phone → Notifications says why in one line ("Notifications are on", or the first reason: the relay unreachable, rate limited or down with its HTTP status, a computer too old to send notifications, or one that refused `push_register` with its own error). Tapping a push whose agent has closed says "That agent has finished"; when no computer has the agent and one could not be asked, it says "<computer> is not reachable". The relay refuses a notify without the grant ([services/push-relay](../services/push-relay/README.md)). Builds without `GOOGLE_SERVICES_JSON` / `GOOGLE_SERVICE_INFO_PLIST` have no token and skip all of this.

**Plain agents (the Mac's hostd, not the desktop app: it works with the Atlas window closed).** hostd stores the token with the paired phone's node id (taken from the connection that sent `push_register`, which needs only `read`, as before) and watches every agent pane's `agent_status`. It notifies on a transition, never on a heartbeat:

| kind | when |
|---|---|
| `agent_done` | a pane that worked goes to done, or its program exits (idle) |
| `agent_needs_you` | a pane starts waiting for an approval (`blocked`) or for the answer to the agent's question (`waiting`) |

Rules: a phone that is connected right now is not pushed (it sees the change live), and one that disconnected is; at most one push per pane and kind every 30 s, so an agent chaining turns is one piece of news; a pane that never worked here (a replay, a daemon that took over) says nothing; a subagent finishing never finishes its parent's pane, so it never pushes, while a subagent's approval prompt (which holds the parent turn) is an `agent_needs_you`; crewmate panes keep their own pushes (`task_done`, `needs_you`). Revoking a phone removes its tokens; a token the relay refuses (`403`, `410`) is dropped. The payload is `{kind, pane, title}` where `title` is `<agent> · <project folder>` (at most 60 characters): never the prompt, the reply, the transcript or the session title. The relay copies those three keys into the FCM data and shows `<title>: An agent finished` or `needs you`; it accepts the two agent kinds only with a pane. **Tapping** the push opens that agent's chat: the app asks each paired Mac for `agent_status_all`, takes the one that has the pane and opens it over the current tab (nothing opens if the agent has since gone away). The app has no in-app notification settings; use the OS notification settings for Atlas. The relay must be deployed with the two new kinds before pushes arrive: an older relay answers `400` to them and hostd keeps the token.

#### Bringing push up

Push has never been switched on (see the status above): the relay is not deployed (`push.codeatlas.com.br` has no DNS record) and the app is built without Firebase config. Two scripts do it, in this order; each takes `--dry-run`, which prints every command and needs no login.

1. **Logins** (you, once; the scripts store none of them): `gcloud auth login` (an owner of the Firebase/GCP project), `firebase login`, `gh auth login` (admin on `codeatlasdev/atlas`, to write environment secrets), and `CLOUDFLARE_API_TOKEN` in the environment with Zone DNS Edit and Zone Origin Rules Edit on `codeatlas.com.br`. A Firebase project must exist (Firebase console, **Add project**, or an existing GCP project with Firebase added); its id is `<project>` below.
2. **The relay**: `GCP_PROJECT=<project> bun run push:deploy` (run `bun run push:deploy --dry-run` first). It enables the APIs, creates the `push-relay` service account (only `roles/firebasecloudmessaging.admin`, the narrowest predefined role with `cloudmessaging.messages.create`, plus read access to its one secret), creates `RELAY_GRANT_KEY` in Secret Manager if absent (never printed, never rotated by the script), builds with Cloud Build, deploys Cloud Run in `southamerica-east1` (0 to 3 instances), points `push.codeatlas.com.br` at it through Cloudflare and ends with a smoke check: `POST /v1/register` answers `200` with a grant and `POST /v1/notify` with a bad grant answers `403`. Why Cloudflare and not a Cloud Run domain mapping: that feature is Preview, "not recommended for production", and not offered in `southamerica-east1`; the script makes a proxied CNAME to the service's `run.app` host and an Origin Rule that rewrites `Host` to it (Cloud Run routes by `Host`).
3. **The app's Firebase config**: `scripts/firebase-mobile-config.sh <project>` registers the Android and iOS apps (`br.com.codeatlas.atlas.mobile` and the Dev id `….mobile.dev`), downloads `google-services.json` and `GoogleService-Info.plist` into a temp dir and stores them as `GOOGLE_SERVICES_JSON` and `GOOGLE_SERVICE_INFO_PLIST` in the `mobile-beta` and `mobile-store` environments, then deletes them. They never touch the repo. The release lanes write the files only for the build and delete them (`write_firebase_config` in `fastlane/Fastfile`); without the secrets the app still builds, with no push.
4. **APNs key, by hand** (iOS only; Firebase has no CLI for it): [developer.apple.com](https://developer.apple.com/account/resources/authkeys/list) → Certificates, Identifiers & Profiles → Keys → **+** → name `Atlas APNs`, tick **Apple Push Notifications service (APNs)** → Continue → Register → **Download** the `.p8` (shown once) and note its Key ID; the Team ID is under Membership details. Then [Firebase console](https://console.firebase.google.com) → the project → the gear icon → **Project settings** → **Cloud Messaging** → **Apple app configuration** → the app `br.com.codeatlas.atlas.mobile` → **APNs authentication key** → **Upload** → the `.p8`, the Key ID, the Team ID. Without it Android push works and iOS push never arrives.
5. **Rebuild the app**: push needs a build that has the config, so ship a release (`bun run mobile:release X.Y.Z`; testers get it first). A build made before step 3 has no push.
6. **Check it end to end with a real phone** (a simulator has no APNs): install the TestFlight or Play internal build, open it, pair a Mac (the app explains notifications after the first pairing: Continue, then Allow), start an agent in a terminal there, send the app to the background (or lock the phone) and let the agent finish or ask for approval. The phone must buzz within seconds, and tapping the push opens that agent's chat. If it does not: `gcloud run services logs read push-relay --region southamerica-east1` (`403` means the phone's grant is stale, so reopen the app once; `502` is FCM, usually the APNs key or the role), and `curl -sS -X POST https://push.codeatlas.com.br/v1/register -d '{"token":"x"}'` must answer `200`.

## Permissions

Atlas never pops a system prompt out of nowhere. Every permission is asked in context, right before the feature needs it, after an Atlas screen that says why and what stays private (Apple guideline 5.1.1, Google's permission guidance), and every refusal leaves a way forward. The code is `lib/core/permissions/`: `PermissionsPort` (status, request, open the system Settings, "was the person told why"; `SystemPermissions` is the real one, `test/support/fake_permissions.dart` the test one), `askPermission` (explanation, then the system prompt) and `PermissionOffCard` (what stopped working, Open Settings, the fallbacks), with every sentence in `permission_copy.dart`.

**One button on iOS, a way out on Android.** The explanation differs per platform because the stores ask for opposite things (`explanationCanDecline`). On iOS it has only **Continue** and cannot be swiped or tapped away: Apple's [HIG, Privacy](https://developer.apple.com/design/human-interface-guidelines/privacy) says "Include only one button", titled "Continue" or "Next", and "don't provide a way for people to leave the screen or window without viewing the system alert". Developers also report App Review rejections of a "Continue" + "Not Now" pre-prompt under guideline 5.1.1(iv). The person says no in the system alert, and the feature's own screen keeps its alternatives (Paste link, the relay). On Android it also has **Not now** and closes like any sheet: Google asks that every educational screen can be cancelled. Every **Not now** below is Android's. Debug and profile builds also ask for Local Network at launch: Flutter's `xcode_backend.dart` adds `NSBonjourServices` (`_dartVmService._tcp`) in those modes so the debugger can find the app, and skips it in release (checked on the dev flavor's release `Info.plist`), so never ship a profile build to TestFlight.

**Where the state comes from.** The official plugin of the feature where it reports the state well, `permission_handler` only where none does: notifications through `firebase_messaging` (`getNotificationSettings`: iOS `denied` is final, Android `deniedPermanently` is, a plain Android `denied` can still be asked again), the device lock through `local_auth` (`isDeviceSupported`, `getAvailableBiometrics`, and its exception codes), the camera through `permission_handler` (the scanner plugin, `mobile_scanner`, reports a refusal only after it opened, and `image_picker` shows the system prompt with no chance to explain first), photos through `image_picker` itself (no permission, below). On iOS `permission_handler` compiles in only the permissions whose usage key the Info.plist has; Atlas has no location or contacts key, so only the camera, microphone and speech codes are in (the plist keys switch them on). The "explained" flags (Face ID, Local Network, the notifications offer) are in `shared_preferences`, per install.

## Atlas updates on the computer

Settings → Computers lists each paired computer with its state and the Atlas it runs (**Connected · Atlas 1.5.0-alpha.25**). When the channel that computer follows offers a newer version, a second row says **Atlas <version> is available**, **On <computer>**. The row only informs: the phone has no **Check now** or **Update** button, so you update on the computer (`atlas update`, or Settings → General → Updates in Atlas Desktop). hostd reads the offer from the check `atlas` already keeps in `~/.atlas/.update_check` (the exit banner and the `atlas dev` prompt use it too), so showing it costs no network call: `info.update` is `{installed, offered, channel, action, checked_at}`, absent until a check of the channel the computer follows is on record.

hostd already serves what an update button would need; the app does not call it yet. `atlas_update_check` (scope `read`) runs the real check on the computer (`atlas update --check --json` of the daemon's own binary, which also refreshes that file), and `atlas_update` (scope `act`) starts the update.

| Command / event | Scope | Does |
|---|---|---|
| `info.update` | `read` | `{installed, offered, channel, action, checked_at}` from the cache; `action` is `update` when `offered` is newer than `installed`, else `none`; absent with no check on record |
| `atlas_update_check {}` | `read` | the CLI's `update --check --json` report `{installed, channel, offered, tag, action, yanked}` (plus `managed`, `manager`, `command` when Homebrew or a package owns the install), and refreshes the cache |
| `atlas_update {}` | `act` | `{started: true, from, to}`; then `atlas_update` events. Refused through `crew_call` |
| `{ev: "atlas_update", stage, message, version}` | `read` | `stage`: `downloading`, `installing`, `handing_off`, `done`, `failed` |

`atlas_update` runs `atlas update --yes` (never `--downgrade`) detached from hostd, so it is the same download, checksum, lock, backup and rollback as typing it in a terminal, and answers `{started: true, from, to}` at once. One runs at a time (a second tap gets `an update is already running`), and it is refused, with the CLI's own words, when nothing newer is offered or when Homebrew or a system package owns this Atlas: those update with `brew upgrade atlas` or the package manager, on the computer. Who started it is written to the audit log (`atlas_update_started {by, from, to}`).

Progress arrives as `{ev: "atlas_update", stage, message, version}` pushes (scope `read`): `downloading`, `installing`, `handing_off` (the terminal host is being replaced by the new one; terminals keep running), then `done` or `failed` (`message` is the CLI's error). The handoff ends the daemon the phone is connected to, so the connection drops and comes back to the new one: `info.version` equal to `to` is the proof the update took, and the phone should treat a drop after `handing_off` as expected, not as "Can't reach Mac". A Windows host has no live handoff: with terminals running it keeps the old host and says so in the `done` message. The `update` capability in `info.caps` tells the phone both commands exist.

## Lab lane (validate a branch without touching your install)

Validating a change to hostd or to the phone app used to mean replacing your installed Atlas and restarting your hostd in the middle of real work. The lab lane runs the branch **beside** your installation, on your real agents:

```bash
bun run mobile:lab                     # build, start the lab hostd, install Atlas Dev on your iPhone, print the pairing QR
bun run mobile:lab --device "<name>"   # a specific device (id or name)    --android | --sim: a physical Android phone, a booted simulator
bun run mobile:lab --watch             # + rebuild and restart the lab hostd on crates/ changes; `flutter run` (debug, hot reload) stays attached
bun run mobile:lab --status            # is the lab running, and what does it follow
bun run mobile:lab --stop              # stops the LAB hostd only
```

**The shadow hostd** (`atlas hostd --lab`, from `target/debug/atlas`; `--dir` overrides the folder) keeps every file under `~/.atlas/lab` (`$ATLAS_HOSTD_DIR/lab`): socket, pid, token, `mobile/key`, `devices.json`, invites and `audit.log`. It never writes under your real directory. It is a *client* of your real hostd's socket:

| It does | How |
|---|---|
| show your real agents | seeds from `agent_status_all` and follows `agent_status` / `agent_approval*` pushes into its own agent hub |
| run the branch's code | `agent_tree`, `agent_history` and `project_*` run in the lab over the same session files and project registry (read only) |
| act on your terminals | `pty_list`, `pty_read`, `pty_write`, `pty_signal`, `pty_open`, `agent_send`, `agent_interrupt`, `agent_approve`, `agent_launch` are forwarded to your hostd; a phone's terminal gets its own connection to it, relayed back, and released when the phone leaves |

It never starts the hook server (that would steal the endpoint your agents read), never adopts or hands off terminals, and refuses to create, kill or resize one. Your hostd holds a permission prompt only for *its own* phones, so an experimental phone never makes a real agent wait. If your hostd restarts (`atlas update`), forwarded calls fail with a clear message and the lab reconnects and re-seeds on its own; with no hostd at all it exits at start with an error. It has no idle timeout: it stops with `--stop`.

The lab lane installs the **Atlas Dev** app ([Dev and store apps](#dev-and-store-apps): flavor `dev`, bundle id `br.com.codeatlas.atlas.mobile.dev`, orange icon), built with `--dart-define=ATLAS_LAB=1 --dart-define=ATLAS_SHA=<git sha>` so it shows a slim `LAB · <sha>` strip on top. Secure storage is isolated by the bundle id (no keychain or app group is shared), and the app has no push (no Firebase or APNs identity), so nothing in it depends on one. The lab pairs with its own code and key; the store app and its pairings are untouched.

Notes: build and install go through `scripts/heavy.sh`; the one-shot path is `flutter build` + `flutter install` (an attached `flutter run --release` hangs, so `--watch` attaches a debug run). A phone must be past its lock screen and trusted for `flutter install`. `atlas.yaml` action `M` runs it.

## Dev and store apps

One codebase, two installable apps, side by side on the same phone (Flutter flavors, [Android](https://docs.flutter.dev/deployment/flavors), [iOS](https://docs.flutter.dev/deployment/flavors-ios)):

| | **Atlas Dev** (flavor `dev`, the default) | **Atlas** (flavor `prod`, the store app) |
|---|---|---|
| Android `applicationId` | `br.com.codeatlas.atlas.mobile.dev` | `br.com.codeatlas.atlas.mobile` |
| iOS bundle id | `br.com.codeatlas.atlas.mobile.dev` | `br.com.codeatlas.atlas.mobile` |
| Name under the icon | Atlas Dev | Atlas |
| Icon | orange (`bun run mobile:dev:icons`) | blue |
| Push | none (no Firebase/APNs identity; entitlements without `aps-environment`) | yes, once configured |
| Where it is defined | Android: product flavor `dev` (`app/build.gradle.kts`, `src/dev/res`); iOS: scheme `dev` and configurations `Debug-dev`, `Profile-dev`, `Release-dev` (`ios/Flutter/*-dev.xcconfig`, `AppIcon-Dev`) | Android: product flavor `prod`; iOS: scheme `prod` over the base `Debug`, `Profile` and `Release` configurations |

The dev app has the orange icon and its own name in **every** build mode (debug, profile, release), so a release-mode build of it is never mistaken for the store app. Its storage, keychain and permissions are its own (the ids differ), so it never reads or overwrites the store app's pairings.

**Plain `flutter run` and `flutter build` make the dev app**: `pubspec.yaml` sets `default-flavor: dev`, which Flutter applies on both platforms (and to `flutter test integration_test`, so the end-to-end test installs the dev app too). A local build therefore cannot replace the store app. In Dart, `appFlavor` (`package:flutter/services.dart`) is `dev` or `prod`.

```bash
flutter run                              # the dev app, debug
flutter run --profile                    # the dev app, profile (orange icon too)
flutter build apk --split-per-abi        # a dev release APK per ABI (sideload)
bun run mobile:lab                       # dev app + lab hostd, see "Lab lane"
```

**Store builds ask for `prod` by name**, never rely on the default: fastlane does (`store_build_args` in `fastlane/Fastfile`: `flutter build ios|appbundle --release --flavor prod --split-debug-info=build/symbols/<platform>`, archive with the `prod` scheme), so `bun run mobile:beta` and the `Mobile release` workflow need nothing extra. By hand: `flutter build appbundle --flavor prod --release` gives `build/app/outputs/bundle/prodRelease/app-prod-release.aab`; `flutter build ipa --flavor prod --no-codesign` gives the `prod` archive. Forgetting `--flavor prod` builds the dev app, which Play and App Store Connect refuse (they know no such app), so the mistake cannot ship the wrong app.

Why flavors and not a project property or `--dart-define`: a flavor is what `flutter run`, the IDEs and `flutter install` understand natively (the old `-Platlab=1` property was invisible to them), Gradle names the outputs per flavor (`app-dev-debug.apk`, `app-prod-release.aab`) and Xcode keeps one scheme per app. The Dart side only needs `appFlavor`; the dart-defines of the lab lane stay for the `LAB` strip and the commit.

To register the dev app for push later, add its ids to the Firebase project (`scripts/firebase-mobile-config.sh` already does); `google-services.json` lists every Android client, so one file serves both flavors.

## Files

Under `~/.atlas/mobile/` (`$ATLAS_HOSTD_DIR/mobile/`): `key` (the computer's iroh identity, 0600), `devices.json` (paired phones and their permissions), `audit.log` (one JSON line per non-read request from a phone, with typed text logged as a length only). `ATLAS_MOBILE_RELAY=0` turns relays and address lookup off (LAN only); `ATLAS_MOBILE_LOOPBACK=1` makes it listen on loopback only (tests; the default is every interface, which a phone on the LAN needs).

## Building the app

Needs the Flutter version pinned in `apps/mobile/pubspec.yaml` (`environment.flutter`, always the newest stable; the gate fails with `flutter upgrade` when yours is older, see `apps/mobile/AGENTS.md`) and a Rust toolchain (the transport is the `apps/mobile/native` crate, bound through flutter_rust_bridge). `scripts/mobile-check.sh` (part of `bun run check`) writes the translations, then runs `flutter analyze` and `flutter test`. It is skipped with a notice when Flutter is not installed.

**Translations.** The app speaks English and Brazilian Portuguese, from the one catalog in `i18n/messages` (areas whose `area.json` says `"surface": "mobile"`; procedure: the `i18n` skill, `.agents/skills/i18n/SKILL.md`). Nothing generated is committed: `bun scripts/i18n/generate.ts --surface mobile` writes `lib/l10n/app_en.arb` and `app_pt.arb` (the language alone: gen_l10n wants a base file, and Atlas has one Portuguese), and `flutter pub get` turns them into `AppLocalizations` (`generate: true`). `mobile-check.sh`, the lab and e2e scripts and the fastlane store builds do both; after you add a message, run the two commands once. A screen reads `context.l10n.some_key` (`core/ui/l10n.dart`). Text not moved to the catalog yet is still English in the code; a new screen uses keys.

`flutter run` and `flutter build` make the **Atlas Dev** app (see [Dev and store apps](#dev-and-store-apps)); a store build says `--flavor prod`. Release sizes and what each build setting is for: [Build settings](#build-settings-size-and-speed).

### Build settings (size and speed)

What the build does, and why (measured 2026-11-15 on Flutter 3.47.7, AGP 9.1.0, Xcode 27.2; the store flavor, release mode, before → after):

| | before | after |
|---|---|---|
| Android APK arm64-v8a (`--split-per-abi`) | 42.3 MB | **34.0 MB** |
| Android APK armeabi-v7a / x86_64 | 33.7 / 46.1 MB | 28.0 / 37.2 MB |
| Android app bundle (`appbundle`, what Play receives) | 105.2 MB | **85.7 MB** |
| `libatlas_mobile_native.so` in the arm64 APK | 13.2 MB | 6.2 MB |
| `libapp.so` (Dart AOT) in the arm64 APK | 8.8 MB | 7.5 MB |
| iOS `Runner.app` of the archive (on disk) | 45.9 MB | **28.7 MB** |
| iOS `Runner.app` zipped (about the IPA's size) | 17.3 MB | **12.2 MB** |
| iOS `atlas_mobile_native.framework` / `App.framework` | 23.3 / 9.7 MB | 8.2 / 8.0 MB |
| iOS debug `Runner.app` (dev) / its native framework | 248 / 83 MB | 196 / 27 MB |

- **Rust (`apps/mobile/native/Cargo.toml`, the biggest piece)**: `opt-level = "s"`, fat LTO and one codegen unit. Measured on `libatlas_mobile_native.so` in the arm64 APK: 13.2 MB with cargo's defaults, 8.2 MB with fat LTO and one unit at `opt-level` 3, 6.2 MB at `s`, 5.6 MB at `z`, 5.3 MB at `s` with `panic = "abort"`. `s` over `3` is a quarter smaller for a crate that moves terminal text, not bulk data; `z` is 9 % smaller still but costs much more speed in crypto-heavy code (one [third-party measurement](https://github.com/Offline-Protocol/offline-protocol-sdk/blob/main/docs/adr/0029-mobile-libraries-are-sized-not-aborting.md): +115 % to +145 % on AES-GCM paths); `panic = "abort"` saves 0.9 MB but turns every panic that flutter_rust_bridge reports to Dart as an exception into a crash of the app, so it stays `unwind`. Debug builds keep line tables (variable info is what made the debug library 83 MB), build dependencies at `opt-level` 2 and the crate at 1, because Rust at level 0 is unusably slow in crypto (not measured here).
- **Dart**: tree-shaken icons are on by default in release (MaterialIcons 1.6 MB → 17 KB). Store builds pass `--split-debug-info=build/symbols/<platform>` (fastlane): the symbols leave the binary, and CI keeps them as the `mobile-symbols-<platform>-<build number>` artifact; `flutter symbolize -i <trace> -d build/symbols/android/app.android-arm64.symbols` reads a stack trace with them. `--obfuscate` is not used: it hides nothing the open repository does not show and makes every report unreadable.
- **Android**: R8 (full mode), resource shrinking and `proguard-android-optimize` are already on for release (Flutter's Gradle plugin; `--no-shrink` has no effect). Release adds `ndk.debugSymbolLevel = SYMBOL_TABLE`, so Play symbolizes a crash in the Rust library. Play receives the bundle and serves each phone only its ABI and density; `--split-per-abi` is for APKs you sideload (the fat one is 115 MB).
- **iOS**: the Xcode Release configuration already has `-O` with whole-module, dead-code stripping and dSYMs; archiving strips the binary (`flutter build ipa`, not `flutter build ios`, for sizes). The obsolete `ENABLE_BITCODE` setting was removed. The Rust static library is force-loaded into its framework, which is why its own size (above) is what counts.
- **Gradle** (`android/gradle.properties`): parallel project execution and the build cache are on. The configuration cache is **off on purpose**: with AGP 9.1 and Flutter 3.47 the first task fails (`Task :app:DevDebugMinSdkCheck … error writing value of type 'java.lang.ref.ReferenceQueue'`, with the report in `build/reports/configuration-cache`). The 8 GB daemon heap is Flutter's template value and fits this Mac. `android.newDsl=false` and `android.builtInKotlin=false` must stay: Flutter's Gradle plugin and its plugins still need the old DSL and the Kotlin plugin (AGP 10, announced for late 2026, removes both flags, so Flutter has to move first; see the [AGP roadmap](https://developer.android.com/build/releases/gradle-plugin-roadmap)).
- **Not done, and why**: a Swift Package Manager plugin. Flutter 3.44+ prefers it and warns that `atlas_mobile_native` does not support it (the CocoaPods path still works, "maintenance mode"), but SPM cannot run `cargo`; flutter_rust_bridge's way out is [native assets](https://cjycode.com/flutter_rust_bridge/manual/integrate/migrate-cargokit-to-native-assets) (`hook/build.dart`, no `rust_builder/`, no cargokit). That migration replaces the whole Rust build path on both platforms, so it is its own change.

Cold times on this Mac (12 cores, `CARGO_BUILD_JOBS=4`): Android debug (4 Rust targets) 5 min, release split APKs 4.5 min, iOS archive 2 min; warm builds recompile only what changed. For a quicker device loop use one ABI: `flutter run --target-platform android-arm64`.

## Launch (no flash between the icon and the first screen)

Tapping the icon shows one colour, the app's ground (`AtlasColors.dark.ground`, `#0B1320`), from the first pixel the OS draws to the first Flutter frame, which is drawn on the same ground; nothing else is on screen before the globe forms in Flutter. The mark is Flutter's on purpose: the entrance animation starts from an empty stage, so a finished globe in the native splash would vanish and form again (the old splash did exactly that). The app is dark only, so there are no night variants.

- **iOS:** `ios/Runner/Base.lproj/LaunchScreen.storyboard` is a view with the ground as an sRGB colour (exact 8-bit fractions: a rounded `0.043` or a P3 colour shows as a step) and no subviews.
- **Android:** `res/values/colors.xml` holds `atlas_ground`; `LaunchTheme` and `NormalTheme` paint it as the window background (`NormalTheme` used the platform's black), and `res/values-v31/styles.xml` styles the Android 12+ system splash: `windowSplashScreenBackground` is the ground and `windowSplashScreenAnimatedIcon` is `drawable/splash_icon.xml`, a transparent square (a drawable without a path makes the system draw the launcher icon, the orange disc the old launch showed). No `postSplashScreenTheme`: that attribute belongs to `androidx.core-splashscreen`; Flutter applies `NormalTheme` itself.
- **Nothing runs before the first frame but `RustLib.init`** (about 10 to 30 ms in a profile build, inside `timeAfterFrameworkInit`). Paired devices come from secure storage after the first frame (Home shows `HomeSplash`, held until the globe has formed) and `PushService.init` starts from `initState`, after it.
- **Guard:** `test/launch_ground_test.dart` reads the storyboard and the Android resources and fails when a native colour differs from the Dart one, when a launch file spells a colour out instead of referencing `@color/atlas_ground`, or when a launch icon comes back.
- **Check a change on a device:** record the launch and sort every frame (`ffmpeg`, Pillow and numpy needed):

  ```sh
  xcrun simctl io booted recordVideo --codec h264 /tmp/launch.mov      # iOS Simulator; Ctrl-C to stop
  adb shell screenrecord --time-limit 7 /sdcard/launch.mp4 && adb pull /sdcard/launch.mp4   # Android
  scripts/mobile-launch-frames.py /tmp/launch.mov
  ```

  It prints the timeline (`GROUND` is the ground colour, `SOLID` a flat white, black or off-colour frame, `OTHER` anything with structure) and exits 1 when a flat off-ground frame follows the first ground frame. The recorders shift dark colours a few steps, so the ground is matched as the recording shows it. `flutter run --profile --trace-startup` writes `build/start_up_info.json` with the time to the first frame; iOS release and profile do not run on the Simulator, so there the frames are from a debug build.

## Goldens

Screenshot tests compare against `apps/mobile/test/goldens/<os>/`: Flutter draws text a few pixels differently on macOS and Linux, so each platform has its own recording and is compared exactly against it (`test/support/per_platform_goldens.dart`). After a visual change, record both: `flutter test --update-goldens` on a Mac writes `macos/`; for `linux/`, push and take the images from the failed CI run's `mobile-golden-failures` artifact (each `<name>_testImage.png` becomes `linux/<name>.png`), or run `--update-goldens` on Linux. A new golden works the same way: a golden missing for the OS the test runs on also leaves the image the run drew in `test/failures/` and fails saying where to copy it. Check that the two sets show the same thing.

## End-to-end test (iOS Simulator, Android emulator)

`bun run mobile:e2e` (`scripts/mobile-e2e.ts`) runs `apps/mobile/integration_test/e2e_test.dart` against a real `atlas hostd`: the app pairs over iroh, lists a fixture project, opens it and a service's sheet, the Agents tab, an agent's chat and its terminal, whose replay must arrive. It touches nothing of yours and never shows a window:

- hostd runs in its own dir under `/tmp` with relays off (`ATLAS_MOBILE_RELAY=0`; the simulator shares the computer's network), with the fixture project and one agent terminal;
- the simulator is a dedicated `atlas-e2e` device, erased on every run (no pairing survives in its Keychain) and booted headless: Simulator.app is never opened.

It takes about two minutes, mostly the iOS build. `bun run mobile:watch` (`--watch`) is the one to look at: it opens Simulator.app on the test device once the app is built, pauses on each step and names it in a banner over the app (1/6 pairing … 6/6 the agent's terminal), the only option that shows a window; `--record <file.mov>` films the simulator screen instead, without showing anything. `--keep` leaves hostd, its dir and the simulator up for a look; `--device "<model>"` picks the simulator model (default iPhone 15 Pro). macOS with Xcode only; it is not part of `bun run check`.

Android: `bun run mobile:e2e:android` / `bun run mobile:watch:android` (`--android`) run the same test on a dedicated `atlas-e2e` emulator (its AVD is created from the newest complete arm64 Google APIs image; your own AVDs are never touched), wiped each run and started without a window unless watching (an emulator cannot be shown after a headless start, so `--watch` shows it from the beginning). It reaches the computer's loopback as `10.0.2.2`. Needs the Android SDK and the Rust Android targets (`rustup target add aarch64-linux-android armv7-linux-androideabi x86_64-linux-android i686-linux-android`). `flutter test` gets `--timeout 5m`, so a stuck step fails with a message.

## Releases (testers, then the stores)

Shipping an update, step by step:

1. Merge the app's changes into `main` (nothing is published).
2. `git checkout main && git pull`.
3. `bun run mobile:release 1.0.1`: a fix bumps the last number, new features the middle one, a big change the first.
4. About 20 minutes later testers have it in TestFlight and Play internal testing (Actions → **Mobile release** shows the run).
5. Try it on a phone.
6. Good: in that run, **Review deployments** → `mobile-store` → **Approve and deploy**. Not good: do not approve; fix, merge and release the next version.
7. Apple reviews (usually 1 to 2 days) and releases on approval; Google reviews and publishes. A store that rejects says why by email; the rejected version never reaches the public.

How it works:

One path, one tag: `bun run mobile:release 1.2.0` (on an up-to-date `main`, clean tree; `--dry-run` prints what it would do) tags `mobile-v1.2.0` and pushes the tag. It refuses a malformed version, an existing tag or one lower than the last mobile release. The tag runs the `Mobile release` workflow (`.github/workflows/mobile-release.yml`, fastlane `apps/mobile/fastlane/Fastfile`):

0. **CI gate:** nothing is built until CI (`ci.yml`) has passed on the tagged commit (`scripts/ci-passed.sh`, the same gate as the desktop and CLI release). A tag on a red or still-running commit waits up to 2 hours for that run and then uploads nothing.
1. **Unattended:** it builds version `1.2.0` (from the tag; `mobile-vX.Y.Z` only) with one build number for both stores, and uploads it to **TestFlight** and the **Play internal testing** track.
2. **After your approval:** the `store` job waits on the `mobile-store` environment. Its required reviewers approve it from the run (**Review deployments**). It then promotes that same build, never a new one: `fastlane ios_release` submits it to App Store review and Apple releases it as soon as it is approved; `fastlane android_release` moves it from internal testing to production, to every user at once. Not approved within 30 days, the run expires and the version stays with testers. A fix is the next tag (`mobile-v1.2.1`).
3. **The APK on the tag:** right after the promotion, the same job downloads Google Play's universal APK of that build (`fastlane android_apk`) and attaches `atlas-mobile-1.2.0.apk` and its `.sha256` to a GitHub release for the tag, created with `--latest=false`. Play signs that APK with its app signing key, the same as a Play Store install, so the two update each other; an APK built and signed in CI would carry the upload key and Android would refuse to update across them. The release is never "Latest" because `/releases/latest` is what the CLI and desktop installers follow, and every client that reads the release list skips `mobile-v` tags (not semver). iOS has no equivalent: Apple allows only the App Store and TestFlight.

Commits and pull requests never publish anything. A run started by hand (Actions, **Run workflow**) builds for testers only and keeps `pubspec.yaml`'s version. Locally, `bun run mobile:beta` does step 1, and `BUILD_NUMBER=<n> VERSION=1.2.0 bundle exec fastlane release` step 2. Nothing secret is in the repo: the lanes read the environment; CI reads the secrets of the `mobile-beta` environment (step 1) and of `mobile-store` (step 2: the App Store Connect key and the Play service account).

Set up once in GitHub: environment `mobile-store` with **Required reviewers** (the maintainers) and **Deployment tags** limited to `mobile-v*`; its secrets `ASC_KEY_ID`, `ASC_ISSUER_ID`, `ASC_KEY_P8`, `PLAY_SERVICE_ACCOUNT_JSON`. Store texts, screenshots, the privacy answers and the age rating are kept in each store's console for now.

| Variable                                                                                            | What                                                                                                                                                                                       |
| --------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `ASC_KEY_ID`, `ASC_ISSUER_ID`, `ASC_KEY_P8`                                                         | App Store Connect API key (role **App Manager**; the `.p8` contents). It uploads the build and signs it (automatic signing, no certificates to manage).                                    |
| `APPLE_TEAM_ID`                                                                                     | The team the app is signed for.                                                                                                                                                            |
| `TESTFLIGHT_GROUPS`                                                                                 | Optional (a CI variable, not a secret): internal TestFlight groups to hand the build to, comma-separated. External testers need Apple's beta review.                                       |
| `BETA_FEEDBACK_EMAIL`                                                                               | Required with `TESTFLIGHT_GROUPS` (a CI variable of `mobile-beta`): the feedback address of the app's TestFlight information. Without it App Store Connect refuses to hand the build to a group. |
| `PLAY_SERVICE_ACCOUNT_JSON`                                                                         | Google Play service account JSON, invited in Play Console with release rights on this app only.                                                                                            |
| `ANDROID_KEYSTORE_BASE64`, `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS`, `ANDROID_KEY_PASSWORD` | The Play upload key (`base64 -i upload.jks`). Locally, `android/key.properties` (git-ignored) works too; without either, a release build is signed with the debug key, which Play refuses. |

Once per store, by hand: create the app record (`br.com.codeatlas.atlas.mobile` on both; `br.com.codeatlas.atlas` is the desktop app), and upload the first Android bundle through Play Console (the API cannot create an app's first release). Testers: an internal TestFlight group (up to 100 team members, no review) and the Play internal testing list (up to 100 emails); each tester gets an invitation link.

**Rehearsal on every pull request that touches the release path** (the workflow, `.github/actions/mobile-store-setup`, `apps/mobile/fastlane`, `ios/`, `android/`, the pubspec and the Ruby files): the same workflow runs only its `rehearsal` jobs, `fastlane ios_rehearse` (macOS: `flutter build ios` and an Xcode archive of the `prod` scheme, unsigned) and `fastlane android_rehearse` (Linux: the `prod` app bundle, debug-signed). Same flavor, flags, Flutter pin and Ruby as a release, no secret, no environment, nothing uploaded, so a broken store build shows up on the pull request instead of on a release tag. Every store job starts from one composite action, `.github/actions/mobile-store-setup` (Flutter from the pubspec, bun, the Rust targets, Ruby from `apps/mobile/.ruby-version`, `bundle install`).

**Store state the pipeline relies on** (set once; checked 2026-11-20): App Store Connect has the 1.0.0 version with description, keywords, screenshots (6.9-inch iPhone), review contact and notes, app privacy (device ID for app functionality, not linked), age rating 4+, content rights (no third-party content), free in every territory. `ios_release` submits through the API key with `precheck_include_in_app_purchases: false` (precheck cannot read in-app purchases through a key) and declares no non-exempt encryption (the Info.plist says so too). Play has every App content task done and the store settings (category Tools, contact `contato@codeatlas.com.br`, site). **The first Play production release is a one-time manual step:** an app never published is a "draft app" and the API refuses to roll anything out on it, so `android_release` creates that first production release as a draft and says so; finish it in Play Console (Publishing overview → Send for review). Every later release goes out from the workflow.

### Store dashboards from an agent (optional)

To see and manage both stores without opening them (testers, build status, review state), a maintainer can add the [app-publish-mcp](https://github.com/mikusnuz/app-publish-mcp) server to their agent. It was read at commit `9d52fb86` (v0.7.0): no telemetry or install scripts; it talks only to `api.appstoreconnect.apple.com` and Google's APIs. Conditions: pin that version (`npx -y app-publish-mcp@0.7.0`); use a dedicated App Store Connect key with the **App Manager** role and a Play service account limited to this app; set every variable in the MCP config (it also reads a `.env` from its working folder); start with `APP_PUBLISH_READ_ONLY=true`. Read-only only hides write tools from the agent, and the report tools can still write files. Without it the agent can submit for review, release to production or delete testers. Keys stay on the maintainer's machine, never in this repo.

### What hostd records for the pane

`mobile_devices` returns each `Device` plus `connected` (a stream from that phone is open now) and `last_seen` (unix seconds: when it last connected or disconnected, kept in `devices.json`, or its newest line in `audit.log` if later; absent until it first connects). `mobile_activity {node_id, limit?}` returns `{activity: [{ts, cmd, args}]}`, newest first, at most 200, read from the end of `audit.log` (the last 512 KiB). `mobile_rename {node_id, name}` renames a phone. All three are desktop-only: a phone gets "not available on mobile". The app still sends no device model or OS, so the pane cannot show them; they need the phone to put them in `pair` (`args.name` today).
